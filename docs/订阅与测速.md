# 订阅、节点与测速

本文是 [开发与架构](开发与架构.md) 的分支，讲清三件事：

1. 多份订阅怎么拉、怎么合并、怎么备份（§1–§2）
2. 选中节点 / 切换国家后，**怎么才真的生效**（§3）
3. 「测速全部」到底怎么跑、判定口径是什么、日志怎么读（§4–§6）

---

## 1. 多订阅：谁负责拉、怎么合并

- **拉取在 `SubscribeConfigActivity`**（设置 → 订阅配置）的 `fetchAll()` / `download()`：逐条**已启用**订阅下载 clash.yml，解析后**按订阅分别缓存**（`SubRaw.<id>` / `SubNodes.<id>`）。
- **订阅页 `SubscribeActivity` 只负责展示合并结果与测速**，不管地址的增删改查。它的节点列表由各订阅缓存合并而成，停用的订阅既不进池、也不进列表。
- 合并口径：所有**已启用**订阅的节点合成一个池（`MihomoConfig.mergedConfig`）；重名节点去重成 `name (N)`（判重必须用 `Set`，见 §5）。
- 测速范围 = 页面上选中的**国家 + 协议**（`filteredNodes()`，刻意不含"显示不可用"）。测速用的那个内核（`CoreTestHost`）也是按**同一份筛选**重建节点池的，所以"你看到的就是被测的、被代理的"——隧道内核的池是连接那一刻的，换过筛选就对不上，因此测速一律走测试内核（见 §4.2）。

### 1.1 本地订阅（备份 / 导入）

`Subscription.local = true` 的订阅内容直接存在 `SubRaw.<id>`，不来自网络：

- `fetchAll()` 会**跳过**它们（否则会把本地内容覆盖掉）；
- `mergedConfig` 对它们与普通订阅**一视同仁**（照样参与合并），所以"备份"就是"一份不会变质的订阅"。

两个来源：

- **订阅备份**（`BackupActivity.doBackup()`，也从订阅页菜单进入）：把所有 `latency >= 0` 的节点，用 `findRawProxy()` 还原各自的原始 clash 块，合成 `proxies:` 文本存成本地订阅（默认**停用**，免得与来源订阅重复合并）。订阅原文里找不到的节点会被跳过并计数上报。
- **导入订阅内容**（`SubscribeConfigActivity.importContent`）：`ClashParser.decodeRaw()` 吃 base64 或明文，解析后同样落本地订阅。「新增订阅」对话框（`showEditDialog(null)`）也接受这个口径：填 `http(s)` 链接就当网络订阅，否则（base64 / 含 `proxies:` 的明文）直接 `saveImportedLocal()`。

另有两条迁移路径，都在订阅配置页菜单与长按「订阅工具」上下文菜单里：**复制全部地址**（每行一个 URL）、**复制全部节点**（各订阅 `proxies:` 段按名字去重合并）。一键替换见 `applyLocalOverride()`（启用目标、停用其余）。

### 1.2 服务器备份

`Preferences.ServerBackup{id, name, activeId, servers}` 存在 `ServerBackups` 键下，与订阅备份**分开存储**：

- 备份 = 深拷贝当前 `SocksServers` + 当时启用中的 id；
- 恢复 = 用备份整体替换服务器列表并恢复启用状态，隧道已连接时发 `ACTION_RECONNECT`；
- 只存本地，**不走 WebDAV**。

### 1.3 WebDAV 远程备份

- 开关与凭据：`Preferences.webdavReady()`（开关开**且**地址非空）；地址 / 用户 / 密码 / 远程目录都在 `Webdav*` 键下。
- 备份时：先**无条件**写一条本地备份记录（历史列表永远有内容、离线也能还原），若 `webdavReady()` 再额外 `WebDav.uploadBackup()` 上传一份；上传失败只反映在 Toast / 日志，本地记录不受影响。
- 导入：`SubscribeConfigActivity.importFromWebdav()` 列目录 → 选一个 → 下载 → 落本地订阅。
- 客户端**只用 GET/PUT/DELETE**（PROPFIND 这类非标准动词在 `HttpURLConnection` 上会抛 `ProtocolException`），所以列目录用一份 `tunvpn-index.txt` 清单文件代替 PROPFIND。因此**云端目录必须事先存在**（WebDAV 不能自动建多级目录）。

## 2. 解析与节点识别

### 2.1 解析（`ClashParser`）

`extractProxies()` 收集 `proxies:` 下**所有协议**的节点，兼容块式与单行内联（flow mapping）两种 YAML 写法；`decodeRaw()` 处理 base64 与明文两种订阅体。

### 2.2 国家识别

`GeoIp` / `MMDB` 把节点服务器 IP 解析成 ISO-3166 国家码，缓存进 `ServerCountryMap`，供国家筛选与自动分组**离线**使用。

- 解析跑在独立的 4 线程池上，`Future.get(3s)` 到点即放弃（返回 null → `UNKNOWN`）；`GeoIp.recentFailures` 记住失败主机 10 分钟。
- 缓存写入合并到每 ~2s 一次，一轮测速结束由 `flushCountryMap()` 收尾（原因见 §5）。

### 2.3 单节点格式互转（`NodeFormat`）

服务器编辑页的「复制 JSON / 复制 Clash / 粘贴」由 `NodeFormat` 提供：clash flow map ↔ JSON 双向转换，粘贴两种格式都接受。

## 3. 节点选择与切换生效链路

### 3.1 运行时事实：`ActiveNode`

- `TProxyService.syncActiveNode()` 读 `GET /proxies/tunvpn` 的 `now` 并写入 `Preferences.ACTIVE_NODE`；`now` 是组时再往下钻（自动模式顶层是某个国家的 url-test 组，真正节点在其下，最多 2 层）。
- `getCurrentNode()` 的取值顺序：**手动上游**（该服务器自己的标签 `协议 · 名字`，无名则 `协议://地址:端口`）→ 订阅模式下若隧道**已连接**用 `ACTIVE_NODE`，否则退回 `SubSelected`。启动与断开时清空，避免残留。
- 采样循环每 ~30 秒同步一次（自动模式下内核自己会换节点）。

> `SubSelected` 只是"愿望"，`ActiveNode` 才是"事实"。首页 / 通知栏显示后者。

### 3.2 启动时应用选择

`applySelectedNode()` 通过控制接口把选中节点应用到真实组。组里已把该节点列在第一位，所以即使控制接口不可用，选择也照样生效。

### 3.3 运行中切换

| 场景 | 链路 |
| --- | --- |
| 订阅页点「使用」 | 发 `ACTION_SELECT`，服务在运行中的内核上直接切换，无需重启 |
| 该节点**不在**运行配置的组里 | `PUT /proxies/tunvpn` 返回非 2xx → `rebuildForSelection()`（主线程 `rebuildTunnel()`）重建配置。仅对**用户主动选择**生效、60 秒去抖；自定义配置不重建（节点本就不在，重建无意义） |
| 切换国家 chip | 已连接时直接发 `ACTION_RECONNECT`（该 action 即"重建配置并立即生效"，`AppListActivity` / `RulesHubActivity` / 服务器启用同一范式） |
| 启用服务器 / 编辑启用中的服务器 / 恢复备份 | 同 `ACTION_RECONNECT` |

> 记住这条：**`config.yaml` 只在启动（或 RECONNECT）时生成**（订阅池、国家筛选、选中节点、代理端口、分流都在里面）。凡是"改了要生效"的设置，要么走 `ACTION_RECONNECT`，要么走 clash-api 的运行时接口（选择器）。只改 SharedPreferences = 只改了愿望。

### 3.4 自动模式

`AutoSelect` 打开时由内核 `url-test` 定时测速自动切换，`interval` 来自 `AutoSelectInterval`（默认 300s，界面按分钟展示）；顶层组默认指向哪个国家组由 `AutoSelectCountry` 决定（空 / `GLOBAL` = 哪儿最快都行）。

## 4. 测速链路

测速走**内核的真实转发延迟**（与 FlClash 同思路），不用 TCP 端口连通性判断可用。

### 4.1 一次「测速全部」的完整流程

1. **单轮互斥**：`TestProgress.begin()`（CAS）拿到本轮 generation。已有轮次在跑 → Toast「上一轮测速还没结束」，不再叠加。
2. **定范围**：`filteredNodes()`（国家 + 协议）；为空则提示而不是静默不动。
3. **按已知延迟排序**（快 → 慢），让用户最关心的节点先出结果。
4. **准备测速内核**（`CoreTestHost.ensureReady`，见 §4.2），失败时若隧道已连接可退回隧道内核的 REST。
5. **单线程自检**（`delaySelfTest`）：用第一个能映射到内核的节点探一次，把「桥的 data 容器形态」「`testDelay` 参数形状」「节点名映射」这三个**一次性闩锁**在并发铺开前定下来。
6. **分组快测**（`fastGroupPhase` → `CoreTestHost.testGroups()`）：逐组触发一次组健康检查，内核**在核内并发**拨测整组，一次桥调用拿回整组延迟。**只补充"可用"结论**，从不写"不可用"。
7. **TCP 负向预筛**（`tcpFastFail`）：对仍无结论的节点本机并行拨一下 `server:port`（32 线程池，`min(2500, max(800, 超时ms))`）。**连不上 ⇒ 判死**（按「无响应判为不可用」记为 `-2` 或 `-1`）；**连得上不写任何结论**，交给内核做权威判定。
8. **逐节点权威探测**（`testNode` → `proxyDelayMs`）：对剩下的节点用内核动作 `testDelay` 探**一次**——用「测速地址」（默认 gstatic `generate_204`）作目标，超时 = 「延迟测试超时」。通即活，失败 / 超时即判（见 §4.4）。
9. **卡住看门狗**（`armStallWatchdog`）：每 15 秒复查一次完成数。阈值两档——本轮还没出过结果时 `max(120s, 超时+15s)`，出过结果后 `max(30s, 超时+15s)`；超时即结束本轮（进度拉满、按钮恢复、Toast + 日志）。
10. **增量落盘**：每 15 个节点 `saveNodes()` 一次（页面已销毁也执行），一轮结束再统一落一次。

准备阶段的三个阶段（加载内核 / 分组快测 / TCP 预筛）都会写进 `TestProgress.phase()`，进度行显示 `正在…`，避免"进度条不动"被误读成卡死。

并发：权威探测固定线程池 **4**（桥只允许一个在途回调，更多线程只是在锁上排队；TCP 预筛另有 32 线程池，不占桥）。整轮**不设总时间预算**，只受单节点超时约束。

### 4.2 测速内核（`CoreTestHost`）

内核 **≠ TUN**：测一个节点只需「内核已加载配置」，不需要建 TUN。为此 App 在**自身进程内**跑一个**无 TUN、无监听**的 mihomo 实例：

- 配置写到 `files/coretest/config.yaml`：`proxies` + **一个 select 组** + 若干 **`lazy: true` 的 url-test 快测组**（每 `TEST_GROUP_SIZE`=48 个节点一组，前缀 `tunvpn-t`）+ `- MATCH,<组>`；**没有 `tun:`、没有 `mixed-port`、没有 `external-controller`**，所以与 `:native` 的隧道内核互不干扰。
- 之所以不用隧道那套分组（每国一个 + 全局一个）：mihomo 一加载配置就会对 `url-test` 组的所有成员**同时**拨测，等于在批量开始前打出一波风暴，我们自己的 `testDelay` 只能排在后面逐个超时——这正是历史问题「选全部一个都不可用、选单国正常」的根因。`lazy: true` 让快测组加载时不自动拨测，需要时才逐组触发。
- **测试内核的节点池 = 当前国家筛选**（`buildTestCoreConfig` → `mergedConfig(prefs)`），所以"测速范围 = 你看到的列表"；这也是旧的「测速并入全量节点」开关被移除的原因。
- 已连接时**也**走测试内核：隧道内核的节点池是**连接时**那一份，换过国家筛选就对不上了。
- `quickSetup` 失败时必须把 `applied` 置否，否则 `isReady()` 会拿着上一次成功应用的状态说"就绪"，探测全打在一个过期节点池上。
- **坏节点隔离**：`mergedConfig` 预检（REALITY `short-id` 必须为偶数长度十六进制 ≤16）；`CoreTestHost` 再从内核报错 `proxy <n>: ...` 反查节点名并排除重试（一次最多 8 个）。mihomo **校验整份配置**，一个非法节点会让**所有**节点都测不了（实测 `proxy 645: invalid REALITY short ID` → 663 个节点全废）。

### 4.3 `testDelay` 的参数形状（内核自己告诉我们的）

1. 外层 `data` 必须是**参数字符串**，不能是内联对象，否则：
   `{"id":"","method":"testDelay","data":"invalid data type","code":-1}`
2. 字符串里 `timeout` 必须是**数字**（int64），传成字符串则：
   `json: cannot unmarshal string into Go struct field TestDelayParams.timeout of type int64`
3. 所以 `CoreTestHost.DELAY_SHAPES[0]` = `{"proxy-name":"...","test-url":"...","timeout":<int>}`。首个被内核接受的形状记在 `delayShape`，整轮复用；`ClashApiServer` 的 `/delay` 用 `CoreTestHost.delayData()` 保持同一形状。

判定口径之所以能保住，全靠 `TProxyService.apiActionRaw()` 拿到原始 `code`：`invalid data type` / `cannot unmarshal` / `json:` 开头的报错都说明"**参数被拒**"，不是节点判定，于是自动换下一种形状（日志：`delay: 动作失败 ...（参数被拒，换形状）`），绝不会因此把节点写成"不可用"。

### 4.4 判定口径（唯一收口点 `noVerdict()`）

| 情形 | 结果 |
| --- | --- |
| 内核明确报失败（HTTP `504` / `408`，或动作返回负数） | `-2` 不可用（与开关无关） |
| **节点级**无响应（探测已发出、超时内没回包） | 由「无响应判为不可用」决定：开（默认）= `-2`，关 = `-1` 未测速 |
| TCP 预筛：端口拨不通（已解析到地址） | 同上开关；`UnknownHostException` / 没有地址 **不判**，交内核 |
| **非节点级**（没有内核、节点不在内核配置里、本轮已放弃） | 一律 `-1` 未测速，绝不写成不可用 |
| 分组快测返回 `0` / 缺失 | 不算结论，交给后续流程复核 |

`ClashNode.latency` 语义：`>=0` 可用（ms）、`-2` 不可用、`-1` 未测速。

**节点如何在跑着的内核里被找到**（`realNodeName`）：

1. **按名字**（`name:<节点名>`）——内核跑的是我们自己生成的配置，名字就是订阅名（含去重后缀）。
2. **按地址**（`server|port`，再带协议类型兜底）——新版内核的 `/proxies` 已经**不再返回 `server`/`port`**，所以这一层大多是空的；类型名（`Shadowsocks`/`Vmess`）与订阅写法（`ss`/`vmess`）也不同，只作二级键。
3. 两层都没命中时，**直接用订阅节点名发探测**（猜错只是一次失败探测），并打日志说明。

## 5. 稳定性与性能硬约束（改这些地方前先读）

一次"测速全部"必须**有界、可结束、可解释**。以下都是硬约束，改动时不要绕过：

| 约束 | 实现 | 为什么 |
| --- | --- | --- |
| **单轮互斥** | `TestProgress.begin()`（CAS）。进行中再点「测速」/ 单节点测速 → 提示「上一轮还没结束」 | 第二轮会把 `pendingTests/testTotal` 重置（单测会把它设成 1），整批计数错乱；同时把上千个探测压到已经满载的内核上 |
| **分组快测** | 测试内核按 48 个节点建一个 `lazy` url-test 组；`testAll()` 在单线程准备阶段调 `CoreTestHost.testGroups()` | 桥只允许一个在途回调 → 逐节点探测天然串行，一轮 ≈ 各节点耗时之和；组健康检查是**核内并发**的，于是大多数可用节点几秒~几十秒一次量完，只剩失败 / 未命中的逐个探测 |
| **TCP 负向预筛** | `tcpFastFail()`，32 线程池，`connectMs = min(2500, max(800, 超时ms))`，总等待 `connectMs+4s` | 死节点每个要吃掉「超时 + 6s」串行时间；拨端口是本机并行的、不占桥。**只判死、绝不判活**，所以口径不变 |
| **并发 = 4** | 探测用 `Executors.newFixedThreadPool(4)` | 桥只允许一个在途回调，16 线程只是 15 个线程在锁上排队 |
| **加载超时=失败** | `ensureReady` 等待 `min(60s, 8s+30ms×节点数)`，超时置 `applied=false` | 几百节点的配置还在解析就开始探测 → 全部不可用 |
| **日志降量** | 批量 `CoreTestHost.setVerbose(false)`，成功探测不再逐行写盘 | 每行日志都要 open/close 一次文件，上千行本身就是卡顿来源 |
| **进度与 DNS 解耦** | `testNode` 里先 `ui.post` 进度、后解析国别；`GeoIp.resolve` 3s 超时 + 独立线程池 | DNS 无超时会冻住进度（表现为"进度一直 0%"） |
| **进度 = 进程级 + 异步** | `TestProgress`（静态持有 `RUNNING/GEN/TOTAL/DONE`），`begin()` 返回 generation；`stale()` 回收"页面已死"的轮次；页面 `onResume` 重新读取 | 测速是**异步**的：切页面、Activity 被重建，回来仍看到真实进度。新一代测速按 generation 取消孤立轮的剩余工作 |
| **增量落盘** | 每 15 个节点 `saveNodes()`，页面已销毁也执行 | 中途切页面 / 进程被杀不丢已测结果 |
| **国别解析只在未知时做** | `testNode` 仅在 `country` 为空 / `UNKNOWN` 时解析；`GeoIp.recentFailures` 记忆失败主机 10 分钟 | 以前每轮每节点都重解析：坏 DNS 下 3s × N，worker 全耗在 DNS 上 |
| **统计口径 = 筛选范围** | `filteredNodes()`（国家 + 协议，**不含**"显示不可用节点"）统一驱动 `sub_stats`、`sub_visible`、`testAll()` 和结束汇总 | "共 N 个"必须是用户选中的范围；同时"不可用 y"在隐藏不可用节点时仍要能报出来 |
| **卡住检测（两档阈值）** | `armStallWatchdog(gen)` 每 15s 复查 `TestProgress.done()`；`stallMsFor(done)`：本轮**尚无结果** → `max(120s, 超时+15s)`，已有结果 → `max(30s, 超时+15s)`，超时即结束本轮 | 旧实现固定 30s、注释却写着 120s：`内核加载 + 分组快测 + TCP 预筛` 在几百上千节点时要跑几十秒，于是"正常但慢"的首轮被误判卡住，剩余全部标未测速 |
| **阶段可见** | `TestProgress.setPhase()`：加载测速内核 / 分组快测 / TCP 预筛；进度行渲染成 `测速中 x/y · 正在…` | 这三个阶段不产生"完成数"，不说明在干什么就一定会被当成卡死 |
| **探测 / 映射只试一次** | `apiHostChecked`、`nameCacheFailed` 记住本轮失败，避免每个节点都重试控制接口探测与 `/proxies` 拉取 | 失败一次就成功不了，逐节点重试等于给整轮加 N 次串行桥调用 |
| **超时只留一个旋钮** | 「延迟测试超时」（1–30s）同时作为内核 `timeout` 与本地等待上界（桥等待 = 超时 + 6s 缓冲） | 早期「每节点测速上限」与「单目标超时」并存时，两个时限互相打架，用户实测"设了没用"；现已合并为单一语义 |
| **判重用 `Set`** | `mergedConfig()` 的 `taken` 必须是 `Set`（`uniqueName()` 用 `contains`） | 用 `List` 判重是 O(n)：600 节点 ≈ 十几万次字符串比较，而这段在每次连接、每次测速前都要跑 |
| **国别映射批量写** | 内存缓存（`loadCountryMap` 按 raw 串比对，变化才重解析）+ 每 ~2s 合并写一次 | `mergedConfig`/`appendAutoGroups` 对每个节点都调 `getServerCountry()`，不缓存就是 O(n²) 次 JSON 解析 + 整文件 commit |
| **节点缓存单趟提交** | `saveNodes()` 单趟按 `subId` 分桶，再 `setSubNodesAll()` 一次 commit | 一轮测速每 15 个节点存一次；逐份订阅各 commit 一次会反复重写含大 blob 的主文件 |

## 6. 测速日志（排查"可用变不可用"）

`TestLog`（`app/src/main/java/com/tunvpn/TestLog.java`）是**全 App 共用的日志文件** `cache/tproxy.log`，就是日志页读取/复制的那份；`TProxyService` 在 `:native`、Activity 在主进程，两边 `TestLog.init()` 后写同一个文件，同时镜像到 logcat（tag `tunvpn`）。

一次"测速全部"会留下（`testAll()` 清空每轮的去重键）：

```
=== 测速开始：N 个节点 · VPN=未连接 · 单次探测超时 5s · 时间预算 不限制（仅按单节点超时控制） · 测速地址 http://www.gstatic.com/generate_204 · 内置目标 4 个 · 国家筛选=全部 · 无响应=不可用 ===

bridge: data 采用字符串形式（内核接受）
delay: 采用参数形状#0（proxy-name/test-url/timeout=n）
delay: 可用 name=... 187ms shape#0 @http://...                             ← 每个串行探到的节点一行
delay: 动作失败 code=-1 data=json: cannot unmarshal string into ... timeout of type int64（参数被拒，换形状）

测速: <内核里的代理名> @http://... -> 无响应（5s 内未判定）/ 失败(-2)

```

**并发下的硬性约定（踩过的坑）**：桥的 `data` 容器（`dataAsString`）、`testDelay` 的参数形状（`delayShape`）、节点名映射（`proxyNameCache`）都是**一次性探测出来的共享闩锁**，必须在批量开始前用**单线程**定下来——`delaySelfTest()` 在 `corePrepared` 置位之前跑一次并打 `测速自检：...`。否则并发探测会把这个闩锁竞争到错误值，然后整轮全部失败，表现为「**单个测速能用、测速全部全废**」。另外：只要本进程已有测试内核，就**不再回退**隧道内核的 REST（那是另一个节点池，只会多花一次往返并刷一屏 502）。

**排查时把从 `=== 测速开始` 到 `=== 测速结束` 的整段贴出来即可**：它能区分「节点真死」与「测试没跑起来」。

## 7. 排查清单

| 症状 | 先看什么 |
| --- | --- |
| 「单个测速能用，测速全部全废」 | `测速自检` 那一行；`bridge:` / `delay:` 行是否有"参数被拒/换形状" |
| 「选全部一个都不可用，选单国正常」 | 分组快测是否命中；`测试内核配置：N 个代理条目` 是否与筛选数一致；是否触发了坏节点隔离（内核 `proxy <n>: ...`） |
| 「进度一直 0%」 | 是否卡在国别解析（DNS 无响应）；`GeoIp.recentFailures` 是否已进入退避 |
| 「卡在 x% 不动」 | 看门狗是否已结束本轮；`bridge: 动作 testDelay 等待 ...ms 未收到回调` |
| 「本来可用，突然全不可用」 | 是否 `本轮 N 个「不可用」全部来自「无响应」`（内核 / 桥沉默），而不是节点全死 |
| 「改了设置没反应」 | 该设置是否走 `ACTION_RECONNECT`，还是只改了 SharedPreferences（见 §3.3） |
