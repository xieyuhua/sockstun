# ProTun 开发与架构

面向开发者：项目结构、从「点连接」到「隧道转发」的完整链路，以及几个关键机制（组件与进程、内嵌内核、配置生成、两层路由）。

排查「连上了但没流量 / 没走代理 / 节点没切换」时可对照本文；更细的分支见：

| --- | --- |

| 统计采样、通知、活跃连接 / 最近请求、持久化、性能约定 | [运行与统计](运行与统计.md) |

- 应用名 / label：`ProTun`
- `namespace` / `applicationId` / Java 包：`com.tunvpn`
- `minSdk 24`，`compileSdk / targetSdk 34`
- 引擎：内嵌 mihomo（`libmihomo-android v0.3.3` → mihomo `v1.19.30`），不是早期的 `libhev-socks5-tunnel`（旧文档里的 `TProxyStartService` / `tproxy.conf` / JNI 契约均已作废）

底部导航：**首页 / 订阅 / 服务器 / 规则 / 设置**（`main.xml` 的 `bottom_nav`；非首页项各自打开独立界面后回到首页高亮）。

## 2. 内嵌内核与动作桥

### 2.1 库与加载

- 依赖：`libmihomo-android` AAR，`app/build.gradle` 固定 `v0.3.3`（mihomo `v1.19.30`），首次构建从 GitHub Releases 下载到 `app/thirdparty/`，只解出 `classes.jar` + `jni/<abi>/*.so`。
- `io.github.oviron.libmihomo.Clash` 是 Kotlin `object`，编译后方法是**实例方法**，Java 侧必须写 `Clash.INSTANCE.xxx()`。

主要调用：

```java
Clash.INSTANCE.load(nativeLibraryDir);              // libclash.so + libmihomo-jni.so
Clash.INSTANCE.quickSetup(homeDir, profile, cb);    // homeDir=files/, profile=config.yaml
Clash.INSTANCE.setEventListener(cb);                // 内核日志
Clash.INSTANCE.startTUN(fd, tunInterface, "tunvpn", stack, address, dns, mtu);
Clash.INSTANCE.invokeAction(actionJson, cb);        // 进程内动作桥
Clash.INSTANCE.getTraffic();                        // {"up":..,"down":..}
Clash.INSTANCE.getTotalTraffic();                   // 累计总量
Clash.INSTANCE.stopTun();
```

### 2.2 进程内动作桥 `apiAction()`

libmihomo 的这个构建**经常不真正监听 external-controller（9090）**的 HTTP 端口，因此 App 的核心数据（连接、节点、切换）主要走**进程内动作桥**，不依赖 HTTP listener：

```
in : {"id":"", "method":"getConnections", "data":null}
out: {"id":"", "method":"getConnections", "data":{...}, "code":0}
```

`TProxyService.apiAction(method, data)` 用 `Clash.INSTANCE.invokeAction()` 发送，阻塞等待回调，`code == 0` 时返回 `data` 的 JSON 字符串（与 REST 响应体同形）。常用 method：

| method | 等价 REST | 用途 |
| --- | --- | --- |
| `getConnections` | `GET /connections` | 连接快照（统计 / 活跃连接） |
| `closeAllConnections` | `DELETE /connections` | 断开全部 |
| `getProxies` | `GET /proxies`、`GET /proxies/{name}` | 节点列表 / 单个组 |
| `changeProxy` | `PUT /proxies/{group}` | 运行时切换节点 |
| `testDelay` | `GET /proxies/{name}/delay` | **隔离的节点延迟测试**（不改全局选择、可并发排队） |
| `startListener` | — | 尝试拉起 external-controller 监听 |

> 该库是 **JNI 优先**设计（FlClash 的内核），**内核自己不会绑定 external-controller**。因此 App 在 `:native` 进程内用 `ClashApiServer` 自建一个回环 HTTP 服务，把 REST 逐条翻译成上面的动作桥——浏览器能访问 `127.0.0.1:<API_PORT>`，`GET /proxies/{name}/delay` 即映射到 `testDelay`。路由清单见 [内核接口参考](内核接口参考.md) §1.2.1。

> **重要：桥只支持单次在途回调。** `apiAction()` 用静态锁 `API_LOCK` 串行化所有调用。若并发调用（例如后台每秒一次的流量轮询与界面自己的轮询重叠），先发起的回调会被后发起的覆盖，导致其永远等不到结果、6 秒超时返回 null——表现为界面「拿不到数据」而后台正常。**任何新增的桥调用都自动受此锁保护，不要绕过 `apiAction()` 直接调 `invokeAction`。**

> **重要：带参数的动作，`data` 必须是 JSON 字符串**，即 `{"id":"","method":"testDelay","data":"{\"proxy-name\":\"...\"}"}`，**不是**内联对象。内核在派发前先校验容器类型，传对象会被回 `{"data":"invalid data type","code":-1}`；而且**只影响带参数的动作**——`getConnections` / `getProxies`（`data` 为 null）完全正常，所以「后台统计/连接列表好用、一测速就全废」就是这么来的。`apiActionRaw()` 现在两种容器都试一次并记住可用的那种（`dataAsString`），日志里会打 `bridge: data 采用字符串形式（内核接受）`。

`bridgeApi()` 把 REST 路径映射到动作；**桥不可用时会自动回退**到 `localApi()`（原始 socket + `protect()` 绕过 VPN + `127.0.0.1:<实际端口>` + `Authorization: Bearer <secret>`）。

### 2.3 端口与跨进程

- `MihomoConfig.pickApiPort()` 在 `9090..9100` 取第一个空闲口，写进 `external-controller`。**`API_PORT` 是每进程一份的静态值**：主进程看到的永远是默认 9090，而 `:native` 可能挑了 9091+。所以 `:native` 选定后立刻 `Preferences.setApiPortActual(port)` 持久化，主进程的测速 / 探测一律读 `getApiPortActual()`。
- `TProxyService` 在 `:native`，**所有 Activity 都在主进程**：主进程里 `Clash.INSTANCE.isLoaded()==false`、`sInstance==null`，所以 Activity **不能**使用进程内桥，也读不到服务的静态字段；`bridgeApi()` 此时回退 HTTP。
- 跨进程数据（统计、连接快照、最近请求、实际端口、`Enable` / `LastError`）通过 `MODE_MULTI_PROCESS` 的 `SharedPreferences` 传递，**写入必须 `commit()`**（`apply()` 不会让别的进程及时看到），读取侧要**新建 `Preferences` 实例**才会刷新。

## 3. 启动流程

三条入口（首页按钮 / 磁贴 / 开机自启）最终都汇聚到 `TProxyService`。Action 一览：

| Action | 语义 |
| --- | --- |
| `tunvpn.CONNECT` | 建立隧道 |
| `tunvpn.DISCONNECT` | 断开并回收 |
| `tunvpn.RECONNECT` | 重建配置并立即生效（改上游 / 作用域 / 规则 / 国家筛选后用它） |
| `tunvpn.SELECT` | 在运行中的内核上切换节点 |
| `tunvpn.RESET_TRAFFIC` | 清零累计计数 |
| `tunvpn.CLOSE_ALL_CONNS` | 在采样线程上断开全部连接并清空快照 |
| `tunvpn.CLEAR_RECENT` | 在采样线程上清空最近请求（内存 + 跟踪表 + 持久化） |

`ACTION_CONNECT` 顺序：

1. **读配置** `new Preferences(this)`（当前档）。
2. **日志重定向**（可选）：反射 `Os.dup2` 把 fd 1/2 指到 `cache/tproxy.log`。
3. **加载内核** `Clash.INSTANCE.load(...)`，失败则写日志 + Toast + `stopSelf()`。
4. **生成配置** `MihomoConfig.build()` → `files/config.yaml`（见 §4）。
5. **建立 VPN** `VpnService.Builder`：
   - 地址 `100.64.0.1/30`（启用 IPv6 时另加 `2001:db8::1/64`）；MTU 固定 `1500`；
   - 路由 `0.0.0.0/0`、`::/0`；DNS 取 `MihomoConfig.dnsFirst(prefs, …)`（与内核 `dns:` 段同源）；
   - 全局模式排除自身（`addDisallowedApplication`）；部分应用模式 `addAllowedApplication` 逐个加入；
   - `setSession("tunVPN/mihomo")`，`establish()` 得到 `tunFd`。
6. **初始化内核** `quickSetup`，homeDir = `files/`，profile = 上一步 `config.yaml`。
7. **订阅内核日志** `setEventListener` → 写进 `tproxy.log`（在 `quickSetup` **之前**挂上，启动期报错才不会丢）。
8. **启动 TUN** `startTUN(fd, protect 回调, ...)`：依次尝试 `gvisor` → `system`，首个成功者生效。
9. **应用选中节点** `applySelectedNode()`（见 [订阅与测速](订阅与测速.md) §3）。
10. **常驻通知** + **统计采样** `startStats()`（见 [运行与统计](运行与统计.md) §1）。
11. **启动自检**：经本机混合端口（`127.0.0.1:<mixed-port>`）对测试地址发一次请求，结果写入日志与首页状态（`proxy_state_*`）；同时打一行 `upstream:` 摘要（当前上游 + 未命中规则的默认去向）。

`stopService()`：`stopStats()` → 置 `Enable=false` → 停前台 → `Clash.INSTANCE.stopTun()` → 关 `tunFd` → `stopSelf()`。

> **TUN 地址为什么要用 `100.64.0.1`**：`172.19.0.1` 落在 `172.16.0.0/12` 私网段里，目标内网恰好也在该段时，TUN 的 `/30` 直连路由会把去往 `172.19.0.x` 的流量截给自己，表现为"代理连上了但访问不到内网 IP"。`100.64.0.0/10` 是运营商级 NAT 保留段，家用 / 企业内网基本不会用到；IPv6 用 RFC 3849 的 `2001:db8::/32` 代替 ULA（`fc00::/7`），同样避免与企业内网撞车。

## 4. 配置生成（`MihomoConfig`）

上游来源只看一件事：**是否启用了某台手动服务器**（`SocksActive`）。

- 启用了 → 用该服务器作上游，**忽略订阅**；
- 未启用 → 用订阅；
- 两者都没有 → 启动失败并提示。

在订阅页点「使用」选用节点时会清除手动服务器的启用（`setActiveSocksId("")`），把上游交还订阅。

### 4.1 合并节点池（订阅模式）

- 解析各启用订阅的 `proxies`，**忽略订阅自带的 `proxy-groups` / `rules`**。
- 按国家筛选（`SubCountryFilter`）过滤后合并、重名去重（`name (2)`…），判重用 `Set`。
- 再把自己产出的 `proxies:` 重新解析一遍来建组，确保组引用一定存在于配置里（否则 mihomo 会因「组引用了不存在的成员」整份配置加载失败）。
- 自建组：
  - **手动模式**：单个 `select` 组 `tunvpn`，把用户选中的节点**列在第一位**（这样即使控制接口不可用，选择也生效）。
  - **自动模式**：每个国家一个 `url-test` 组（`tunvpn-<CC>`）+ 一个全局 `url-test` 组（`tunvpn-global`），再由顶层 `select` 组 `tunvpn` 指向它们。

组名常量：`MihomoConfig.GROUP = "tunvpn"`、`GLOBAL_GROUP = "tunvpn-global"`、`countryGroup(cc) = "tunvpn-<cc>"`。

### 4.2 路由规则

`appendRules()` 依据 `RulesStrategy`：

- 全局代理 → `MATCH,tunvpn`
- 全局直连 → `MATCH,DIRECT`
- 规则模式 → 用户规则逐条（`DOMAIN-SUFFIX` / `DOMAIN` / `DOMAIN-KEYWORD` / `GEOSITE` / `GEOIP` / `IP-CIDR[6]` / `PROCESS-NAME` / `PROCESS-PATH` / `DST-PORT` / `SRC-PORT` / `NETWORK`）→ 兜底 `MATCH,tunvpn|DIRECT`

### 4.3 手动上游节点

`manualSocksConfig()` 生成一个只含该服务器的 `proxies:` 条目（SOCKS5 时）：

- `server` / `username` / `password` 一律加引号并做 **YAML 转义**——地址里有 `:`、`#`、空格或密码里带引号时，裸值会让 mihomo 以 `yaml: mapping values are not allowed` 拒掉整份配置，或把密码截断成另一个字段。
- `udp:` 由 **「UDP relay over TCP」** 决定：勾选时写 `udp: false`（只走 CONNECT，适配只转发 TCP 的 frp / 内网穿透），否则 `udp: true`。
- 非 SOCKS5 协议则直接搬运用户粘贴的原始 clash 定义（`raw`），同样做转义与重命名。

### 4.4 追加的必需段

`config.yaml` 由 App 生成时补齐（已存在则不覆盖）：

- `dns:`（`MihomoConfig.dnsSection()` 按规则页设置生成）：远程 DNS **开** → `fake-ip` `198.18.0.1/16` + `fake-ip-filter`（`localhost`、`*.local`；**不过滤**内网业务域名，它们需要 fake-ip 才能把域名原样送到代理端解析）；**关** → `redir-host`，有自定义 DNS 时再加 `respect-rules`。`nameserver` = 自定义 IPv4/IPv6（仅远程 DNS 关闭时）+ 公网 `223.5.5.5` / `119.29.29.29`。`VpnService.Builder` 与 TUN 启动参数用 `dnsFirst()` / `dnsCsv()` 取同一组；
- `log:`（写 `cache/mihomo.log`）
- `tun:`（enable + auto-route + auto-detect-interface + `dns-hijack: any:53`）
- `external-controller: 127.0.0.1:<API_PORT>` + `secret: "<token>"`；端口由 `pickApiPort()` 在 `9090..9100` 中取第一个空闲口，并持久化到 `ApiPortActual`
- `mode: rule`、`unified-delay`、`tcp-concurrent`、`ipv6: false`、`find-process-mode: always`、`external-controller-cors`
- `mixed-port: <ProxyPort>`（默认 7890）；`allow-lan` 仅在开启时写入
- 含 GEOIP/GEOSITE 规则时才开 `geo-auto-update`，下载走 jsdelivr 镜像

文件必须命名 `config.yaml`（内核按此名加载，否则 `quickSetup` 报 `stat config.yaml: no such file`）。

**自定义配置模式**（`CustomConfig`）：直接加载用户编辑过的 `files/config.yaml`，但仍做一次「必需项对齐」——`external-controller` 改写为 `127.0.0.1:<API_PORT>`、补齐 `secret` 与 `mixed-port`。强制回环的原因：本构建里 mihomo 绑 `0.0.0.0` 会静默失败（"9090 never listens"）。

## 5. 两层路由

```
App 产生数据包
  │
  ▼ ① VpnService 作用域（建 VPN 时）
  │    全局（默认）：全部 App 进 TUN（排除自身）
  │    部分应用：仅白名单进 TUN；其余走原网络
  │
  ▼ ② 进 TUN 的包 → mihomo 路由策略
  │    全局代理 / 全局直连：直接短路由
  │    规则模式：逐条匹配用户规则 → 兜底 MATCH
  │
  ▼ ③ 命中代理 → tunvpn 组（自动 url-test / 手动 select）
  │
  ▼ ④ 经 protect() 保护的外出 socket 转发到真实节点
```

- 第 ① 层是**按 App 的粗粒度过滤，先于**第 ② 层；被排除的 App 完全不受规则影响。
- 代码：`TProxyService` 用 `addAllowedApplication` / `addDisallowedApplication` 决定作用域（`prefs.getGlobal()` / `getApps()`，`getGlobal()` 默认 `true`）；`MihomoConfig.appendRules` 输出 `rules:`。
- 部分应用但 `getApps()` 为空时无流量进隧道，规则页会红色告警，服务器页启用时也会提示。
