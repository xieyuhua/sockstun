# ProTun 开发与架构

面向开发者：说明项目结构、从「点连接」到「隧道转发」的完整链路，以及几个关键机制（配置生成、两层路由、内核动作桥、测速、统计）。排查「连上了但没流量 / 没走代理 / 节点没切换」时可对照本文。

- 应用名 / label：`ProTun`
- `namespace` / `applicationId` / Java 包：`com.tunvpn`
- `minSdk 24`，`compileSdk / targetSdk 34`
- 引擎：内嵌 mihomo，不是早期的 `libhev-socks5-tunnel`（旧文档里 `TProxyStartService` / `tproxy.conf` / JNI 契约均已作废）

## 2. 内嵌内核与动作桥

### 2.1 库与加载

- 依赖：`libmihomo-android` AAR，`app/build.gradle` 固定 `v0.3.3`（mihomo `v1.19.30`），首次构建从 GitHub Releases 下载到 `app/thirdparty/`，只解出 `classes.jar` + `jni/<abi>/*.so`。
- `io.github.oviron.libmihomo.Clash` 是 Kotlin `object`，编译后方法是**实例方法**，Java 侧必须写 `Clash.INSTANCE.xxx()`。

主要调用：

```java
Clash.INSTANCE.load(nativeLibraryDir);              // libclash.so + libmihomo-jni.so
Clash.INSTANCE.quickSetup(homeDir, profile, cb);    // homeDir=files/, profile=config.yaml
Clash.INSTANCE.setEventListener(cb);                // 内核日志
Clash.INSTANCE.startTUN(fd, tunInterface, "tunvpn", stack, address, dns, mtu);
Clash.INSTANCE.invokeAction(actionJson, cb);        // 进程内动作桥
Clash.INSTANCE.getTraffic();                        // {"up":..,"down":..}
Clash.INSTANCE.getTotalTraffic();                   // 累计总量
Clash.INSTANCE.stopTun();
```

### 2.2 进程内动作桥 `apiAction()`

libmihomo 的这个构建**经常不真正监听 external-controller（9090）**的 HTTP 端口，因此 App 的核心数据（连接、节点、切换）主要走**进程内动作桥**，不依赖 HTTP listener：

```
in : {"id":"", "method":"getConnections", "data":null}
out: {"id":"", "method":"getConnections", "data":{...}, "code":0}
```

`TProxyService.apiAction(method, data)` 用 `Clash.INSTANCE.invokeAction()` 发送，阻塞等待回调，`code == 0` 时返回 `data` 的 JSON 字符串（与 REST 响应体同形）。常用 method：

| method | 等价 REST | 用途 |
| --- | --- | --- |
| `getConnections` | `GET /connections` | 连接快照（统计 / 活跃连接） |
| `closeAllConnections` | `DELETE /connections` | 断开全部 |
| `getProxies` | `GET /proxies`、`GET /proxies/{name}` | 节点列表 / 单个组 |
| `changeProxy` | `PUT /proxies/{group}` | 运行时切换节点 |
| `testDelay` | `GET /proxies/{name}/delay` | **隔离的节点延迟测试**（FlClash 同款；不改全局选择、可并发） |
| `startListener` | — | 尝试拉起 external-controller 监听 |

> 该库是 **JNI 优先**设计（FlClash 的内核），**内核自己不会绑定 external-controller**。因此 App 在 `:native` 进程内用 `ClashApiServer` 自建一个回环 HTTP 服务，把 REST 逐条翻译成上面的动作桥——这样浏览器能访问 `127.0.0.1:<API_PORT>`，App 自己的 REST 路径（测速）也有了对端。`GET /proxies/{name}/delay` 即映射到 `testDelay`。

> **重要：桥只支持单次在途回调。** `apiAction()` 用静态锁 `API_LOCK` 串行化所有调用。若并发调用（例如后台每秒一次的流量轮询与界面自己的轮询重叠），先发起的回调会被后发起的覆盖，导致其永远等不到结果、6 秒超时返回 null——表现为界面「拿不到数据」而后台正常。**任何新增的桥调用都自动受此锁保护，不要绕过 `apiAction()` 直接调 `invokeAction`。**

> **重要：带参数的动作，`data` 必须是 JSON 字符串**，即 `{"id":"","method":"testDelay","data":"{\"proxy-name\":\"...\"}"}`，**不是**内联对象。内核在派发前先校验容器类型，传对象会被回 `{"data":"invalid data type","code":-1}`；而且**只影响带参数的动作**——`getConnections` / `getProxies`（`data` 为 null）完全正常，所以「后台统计/连接列表好用、一测速就全废」就是这么来的，极难从现象上看出来。`apiActionRaw()` 现在两种容器都试一次并记住可用的那种（`dataAsString`），日志里会打 `bridge: data 采用字符串形式（内核接受）`。

`bridgeApi()` 把 REST 路径映射到动作；**桥不可用时会自动回退**到 `localApi()`（原始 socket + `protect()` 绕过 VPN + `127.0.0.1:API_PORT` + `Authorization: Bearer <secret>`），`/proxies/{name}/delay` 则始终走 HTTP。

> **跨进程注意（关键）**：`TProxyService` 在 `:native` 进程，而所有 Activity 都在**主进程**。主进程里 `Clash.INSTANCE.isLoaded()==false`、`sInstance==null`，所以 Activity **不能**使用进程内桥，也读不到服务的静态字段；`bridgeApi()` 此时回退到 HTTP。跨进程的数据（统计、连接快照、最近请求、`Enable` / `LastError`）一律通过 `MODE_MULTI_PROCESS` 的 `SharedPreferences` 传递，**写入必须 `commit()`**（`apply()` 不会让别的进程及时看到），读取侧要**新建 `Preferences` 实例**才会刷新。

## 3. 启动流程

三条入口（首页按钮 / 磁贴 / 开机自启）最终都汇聚到 `TProxyService`。`ACTION_CONNECT` 顺序：

1. **读配置** `new Preferences(this)`（当前档）。
2. **日志重定向**（可选）：反射 `Os.dup2` 把 fd 1/2 指到 `cache/tproxy.log`。
3. **加载内核** `Clash.INSTANCE.load(...)`，失败则写日志 + Toast + `stopSelf()`。
4. **生成配置** `MihomoConfig.build()` → `files/config.yaml`（见 §4）。
5. **建立 VPN** `VpnService.Builder`：
   - 地址 `172.19.0.1/30`（IPv6 时另加 `fc00::1/64`），MTU `prefs.getTunnelMtu()`；
   - 路由 `0.0.0.0/0`、`::/0`；DNS `223.5.5.5` / `2400:3200::1`；
   - 全局模式排除自身（`addDisallowedApplication`）；部分应用模式 `addAllowedApplication` 逐个加入；
   - `setSession("tunVPN/mihomo")`，`establish()` 得到 `tunFd`。
6. **初始化内核** `quickSetup`，homeDir = `files/`，profile = 上一步 config.yaml。
7. **订阅内核日志** `setEventListener` → 写进 `tproxy.log`。
8. **启动 TUN** `startTUN(fd, protect 回调, ...)`：依次尝试若干 stack（`gvisor` 等），首个成功者生效。
9. **应用选中节点** `applySelectedNode()`（见 §6）。
10. **常驻通知** + **统计采样** `startStats()`（见 §7）。
11. **启动自检**：通过本机混合端口（`127.0.0.1:<mixed-port>`）对测试地址发一次请求，结果写入日志与首页状态（`proxy_state_*`）。

`stopService()`：`stopStats()` → 置 `Enable=false` → 停前台 → `Clash.INSTANCE.stopTun()` → 关 `tunFd` → `stopSelf()`。

## 4. 配置生成（`MihomoConfig`）

上游来源只看一件事：**是否启用了某台手动服务器**（`SOCKS_ACTIVE`）。

- 启用了 → 用该服务器作上游，**忽略订阅**；
- 未启用 → 用订阅；
- 两者都没有 → 启动失败并提示。

在订阅页点「使用」选用节点时会清除手动服务器的启用（`setActiveSocksId("")`），把上游交还订阅。

### 4.1 合并节点池（订阅模式）

- 解析各启用订阅的 `proxies`，**忽略订阅自带的 `proxy-groups` / `rules`**。
- 按国家筛选（`SubCountryFilter`）过滤后合并、重名去重（`name (2)`…）。
- 再把自己产出的 `proxies:` 重新解析一遍来建组，确保组引用一定存在于配置里（否则 mihomo 会因「组引用了不存在的成员」整份配置加载失败）。
- 自建组：
  - **手动模式**：单个 `select` 组 `tunvpn`，把用户选中的节点**列在第一位**（这样即使控制接口不可用，选择也生效）。
  - **自动模式**：每个国家一个 `url-test` 组（`tunvpn-<CC>`）+ 一个全局 `url-test` 组（`tunvpn-global`），再由顶层 `select` 组 `tunvpn` 指向它们。

组名常量：`MihomoConfig.GROUP = "tunvpn"`、`GLOBAL_GROUP = "tunvpn-global"`、`countryGroup(cc) = "tunvpn-<cc>"`。

### 4.2 路由规则

`appendRules()` 依据 `RulesStrategy`：

- 全局代理 → `MATCH,tunvpn`
- 全局直连 → `MATCH,DIRECT`
- 规则模式 → 用户规则逐条（`DOMAIN-SUFFIX` / `DOMAIN` / `DOMAIN-KEYWORD` / `GEOIP` / `GEOSITE` / `IP-CIDR[6]` / `PROCESS-NAME` / `PROCESS-PATH` / `DST-PORT` / `SRC-PORT` / `NETWORK`）→ 兜底 `MATCH,tunvpn|DIRECT`

### 4.3 追加的必需段

`config.yaml` 由 App 生成时补齐（已存在则不覆盖）：

- `dns:`（fake-ip `198.18.0.1/16`，nameserver `223.5.5.5` / `119.29.29.29`）
- `log:`（写 `cache/mihomo.log`）
- `tun:`（enable + auto-route + auto-detect-interface + `dns-hijack: any:53`）
- `external-controller: 127.0.0.1:<API_PORT>` + `secret: "<token>"`（`API_PORT` 由 `pickApiPort()` 在 `9090..9100` 中取第一个空闲口）
- `mode: rule`、`unified-delay`、`tcp-concurrent`、`ipv6: false`、`find-process-mode: always`、`external-controller-cors`
- `mixed-port: <ProxyPort>`（默认 7890）；`allow-lan` 仅在开启时写入
- 含 GEOIP/GEOSITE 规则时才开 `geo-auto-update`，下载走 jsdelivr 镜像

文件必须命名 `config.yaml`（内核按此名加载，否则 `quickSetup` 报 `stat config.yaml: no such file`）。

## 5. 两层路由

```
App 产生数据包
  │
  ▼ ① VpnService 作用域（建 VPN 时）
  │    全局：全部 App 进 TUN（排除自身）
  │    部分应用：仅白名单进 TUN；其余走原网络
  │
  ▼ ② 进 TUN 的包 → mihomo 路由策略
  │    全局代理 / 全局直连：直接短路由
  │    规则模式：逐条匹配用户规则 → 兜底 MATCH
  │
  ▼ ③ 命中代理 → tunvpn 组（自动 url-test / 手动 select）
  │
  ▼ ④ 经 protect() 保护的外出 socket 转发到真实节点
```

- 第 ① 层是**按 App 的粗粒度过滤，先于**第 ② 层；被排除的 App 完全不受规则影响。
- 代码：`TProxyService` 用 `addAllowedApplication` / `addDisallowedApplication` 决定作用域（`prefs.getGlobal()` / `getApps()`）；`MihomoConfig.appendRules` 输出 `rules:`。
- 部分应用但 `getApps()` 为空时无流量进隧道，规则页会红色告警。

## 6. 订阅与节点

### 6.1 解析（`ClashParser`）

`extractProxies()` 收集 `proxies:` 下**所有协议**的节点，兼容块式与单行内联（flow mapping）两种 YAML 写法。

### 6.2 节点国家识别

`GeoIp` / `MMDB` 把节点服务器 IP 解析成 ISO-3166 国家码，缓存进 `ServerCountryMap`，供国家筛选与自动分组离线使用。

### 6.3 节点选择

- 启动时 `applySelectedNode()` 通过控制接口把选中节点应用到真实组。
- 运行中：订阅页点「使用」发 `ACTION_SELECT`，`TProxyService` 在运行中的内核上直接切换，无需重启。
- 自动模式（`AutoSelect`）下由内核 `url-test` 定时测速自动切换，`interval` 来自 `AutoSelectInterval`（默认 300s）。

## 7. 延迟测试

`SubscribeActivity` 的测速走**内核的真实转发延迟**（与 FlClash 相同思路），不再用 TCP 端口连通性：

```
GET /proxies/{name}/delay?timeout=<ms>&url=<testUrl>
→ 成功 {"delay": 123}；失败 HTTP 504 / 非 200
```

- 判定语义（`ClashNode.latency`）：`>=0` 可用（ms）、`-2` 不可用、`-1` 未测速。
- **节点定位按 `地址|端口`**（`realNodeName`）：mihomo 报的协议名是 `Shadowsocks`/`Vmess`，订阅里是 `ss`/`vmess`，若按协议名做键会永远匹配不到、测不了。
- **判定口径（关键，避免好节点被误判）**：只有内核真实返回 `504/408`（经该节点无法完成探测）才判 `-2`；其它非 200（401 鉴权 / 404 路由 / 参数错误 / 其它 5xx）只说明"测试没能跑起来"，一律按**未测速**处理。
- 多个候选目标（用户配置的测速地址优先，随后内置 gstatic / google / msftconnecttest / cloudflare），任一可达即视为可用。
- 首轮全部真失败时，会用**更长超时**在 cp.cloudflare.com / gstatic 上做一次救援探测，避免慢节点被 5 秒超时误杀（等价于旧兜底但不改全局选择）。
- 并发用固定线程池（16）限流；结果与节点缓存一起持久化。

> 早期版本会在 `/delay` 失败后「临时把该节点设为当前节点再发一次真实请求」作为兜底；该做法会改动全局选择并误伤正常节点，**已移除**。

#### 7.0 稳定性约束（几百上千节点也不崩）

一次"测速全部"必须**有界、可结束、可解释**。以下都是硬约束，改动时不要绕过：

| 约束 | 实现 | 为什么 |
| --- | --- | --- |
| **单轮互斥** | `passRunning`（CAS）。进行中再点「测速」/单节点测速 → Toast「上一轮还没结束」 | 第二轮会把 `pendingTests/testTotal` 重置（单测会把它设成 1），整批计数错乱；同时把上千个探测压到已经满载的内核上 |
| **并发降为 4** | `Executors.newFixedThreadPool(4)` | 进程内桥只允许一个在途回调，16 线程只是 15 个线程在锁上排队，纯内存/调度压力 |
| **时间预算** | `passBudgetMs(n)=min(8min, 45s+2s×n)`，到期后 `passExpired()` 让余下节点直接判未测速（记 `passSkipped`） | 几百个死节点无论怎么限时都测不完；预算保证**一定会结束**，且不会谎报测过 |
| **批量收紧超时** | 批量时单目标超时 `min(设置, 6s)`，救援探测 10s，且**连续 2 次硬失败即转救援** | 设置 30s 时，一个死节点原本要 4×30+2×30=3 分钟 |
| **加载超时=失败** | `ensureReady` 等待 `min(60s, 8s+30ms×节点数)`，超时置 `applied=false` | 原来固定 8s 超时后**当作成功**，几百节点的配置还在解析就开始探测 → 全部不可用（单国配置小，8s 内加载完，所以正常） |
| **日志降量** | 批量 `CoreTestHost.setVerbose(false)`，成功探测不再逐行写盘 | 每行日志都要 open/close 一次文件，上千行本身就是卡顿来源 |
| **看门狗** | 60s 零进展 → 记日志 + 强制 `releasePass()` 并结束本轮 | 卡死的轮次不能让按钮永久失效 |
| **进度与 DNS 解耦** | 先 `ui.post` 进度、后解析国别；`GeoIp.resolve` 3s 超时 | DNS 无超时会冻住进度（见 §7.2） |
| **进度 = 进程级 + 异步** | `TestProgress`（静态持有 `RUNNING/GEN/TOTAL/DONE/deadline`）。`begin()` 返回 generation，`nodeDone(gen)` 只计本轮，`stale()` 回收"页面已死"的轮次；页面在 `onResume` 重新读取 | 测速是**异步**的：切走页面、甚至 Activity 被重建，回来仍能看到真实进度，而不是从 0% 开始。新一代测速按 generation **取消孤立轮的剩余工作** |
| **增量落盘** | 每 `INCREMENTAL_SAVE_EVERY`(15) 个节点 `saveNodes()`，页面已销毁时也执行 | 中途切页面/进程被杀不丢已测结果 |
| **国别解析只在未知时做 + 失败退避** | `testNode` 仅在 `country` 为空/UNKNOWN 时解析；`GeoIp.recentFailures` 记忆失败主机 10 分钟 | 以前 `refresh=true` 每轮每节点都重解析：坏 DNS 下 3s × N，worker 全耗在 DNS 上（这是"测速很慢"的主因之一） |
| **批量探测量收紧** | 批量单目标 **4s**、连续 **1** 次硬失败即转救援、救援只试 **1** 个目标（8s） | 单节点仍走完整多目标（2 次失败 + 2 个救援目标），兼顾"快"与"不误判" |
| **统计口径 = 筛选范围** | `filteredNodes()`（国家 + 协议，**不含**"显示不可用节点"）统一驱动 `sub_stats`、`sub_visible`、`testAll()` 和结束汇总 | "共 N 个"必须是用户选中的范围；同时"不可用 y"在隐藏不可用节点时仍要能报出来 |
| **国别解析不占探测线程** | `geoPool`（独立单线程）异步解析，`resolveCountryAsync()`；`testNode` 只负责探测 | 国别解析每主机可能 3s DNS + 2×3s HTTP 兜底，占着 4 个探测 worker 就等于整轮慢几倍（这是"测速太慢"的主要隐形来源） |
| **耗时可见** | `测速: 内核准备耗时 Xms`、慢节点 `探测耗时 Xms（含多目标尝试与救援）`、每轮收尾 `测速耗时: 本轮…平均…最慢…`；进度行带 `剩余约 N 秒` | 桥是单回调，**整轮 ≈ 各探测之和**；没有这些行就只能靠猜时间花在哪 |
| **单节点时间上限** | `NodeTestLimit`（设置 → 订阅，默认 15s，5–120）；`proxyDelayMs` 内 `nodeDeadline` 同时约束目标循环与救援探测，且 ≥ 单目标超时+1s | 一个节点可能发多次探测；没有上限时"无判定"会走满 4 个目标 × 9s ≈ 36s，几百个节点就把一轮拖到看起来卡死 |
| **无判定即止损** | `delayProbe` 返回 null（桥无回包 / 控制接口不可达 / 回包无法解析）时**立即返回**，不再换目标重试 | null 是"管道坏了"而不是"这个目标不行"；继续换目标只是把同样的沉默重复 4 遍 |
| **卡住检测** | `armStallWatchdog(gen)` 每 15s 复查 `TestProgress.done()`；超过 `max(60s, 单节点上限+15s)` 没有新结果 → 结束本轮（DONE 拉满、按钮恢复、Toast + 日志说明） | 旧看门狗只在"一个结果都没有"时触发，于是**卡在 7% 就永久卡住**；现在只看"有没有在前进" |
| **探测/映射只试一次** | `apiHostChecked`、`nameCacheFailed` 记住本轮的失败，避免每个节点都重试控制接口探测与 `/proxies` 拉取 | 失败一次就成功不了，逐节点重试等于给整轮加 N 次串行桥调用 |
| **坏节点隔离** | `mergedConfig` 预检（REALITY `short-id` 必须为偶数长度十六进制 ≤16）；`CoreTestHost` 再从内核报错 `proxy <n>: ...` 反查节点名并排除重试（一次最多 8 个） | mihomo **校验整份配置**，一个非法节点就让**所有**节点都测不了（实测 `proxy 645: invalid REALITY short ID` → 663 个节点全废）——这正是「全部国家全不可用、选单国却正常」的根因 |

### 7.1 未连接 VPN 也能测速（`CoreTestHost`）

内核 **≠ TUN**：测一个节点只需「内核已加载配置」，**不需要建 TUN / 连 VPN**（TUN 只是内核的一个入口）。为此 App 在**自身进程内**再跑一个 **无 TUN、无监听**的 mihomo 实例：

- 配置写到 `files/coretest/config.yaml`：`proxies` + **一个 select 组** + `- MATCH,<组>`，**没有 `tun:`、没有 `mixed-port`、没有 `external-controller`**——所以它和 `:native` 里的隧道内核互不干扰。
- **刻意不带 url-test 组**：mihomo 一加载配置就会对 url-test 组的所有成员**同时**发起健康检查。测速内核如果沿用隧道的分组（每个国家一个 + 一个覆盖全部的全局组），「全部」时会瞬间打出近百个并发探测，我们自己的 `testDelay` 只能排在这波风暴后面、逐个超时——**这就是「选全部一个都不可用、选单国正常」的根因**。测速只要节点，不需要任何周期性健康检查。
- 测速优先走内核动作 **`testDelay`**（隔离 URLTest，FlClash 同款）：`delayProbe()` 先试它，拿不到再回退到内嵌 HTTP 的 `/delay`。
- **测试内核的节点池 = 当前国家筛选**（`buildTestCoreConfig` → `mergedConfig(prefs)`），所以"测速范围 = 你看到的列表"：选「全部」就测全部节点，选某个国家就测该国全部节点。这正是**「测速并入全量节点」开关被移除**的原因——不需要它，筛选本身就是范围；同时 `testAll()` 也只对筛选范围内的节点发探测，不会再去测列表外的节点。
- 效果：**未连接时也能做"内核真实转发"测速**；已连接时也走这个测试内核（隧道内核的节点池是**连接时**那一份，换过国家筛选就对不上了）。
- `quickSetup` 失败时必须把 `applied` 置否（`CoreTestHost.ensureReady`）：否则 `isReady()` 会拿着**上一次**成功应用的状态说"就绪"，探测就全打在一个过期的节点池上。

设置 → 订阅 里的开关：

| 开关 | 键 | 作用 |
| --- | --- | --- |
| 未连接时内核测速 | `PreloadCore` | 未连接时是否**预加载**测试内核（`onResume` 里后台加载），让首次测速立刻开始；关=不预加载，点「测速」时按需加载（`prepareTestCore` 始终 `ensureReady`） |
| 显示不可用节点 | `ShowUnavailable` | 列表是否同时列出 `-2`（不可用）与 `-1`（未测速）的节点；关=只显示可用节点 |
| 无响应判为不可用 | `ProbeTimeoutAsFail` | 节点级"无响应 / 时限用尽"记为 `-2`（默认开）还是 `-1`（关）；见 §7.2 判定收口 |

### 7.2 测速日志（排查"可用变不可用"）

`TestLog`（`app/src/main/java/com/tunvpn/TestLog.java`）是**全 App 共用的日志文件** `cache/tproxy.log`，就是 日志页 读取/复制的那份；`TProxyService` 在 `:native`、Activity 在主进程，两边 `TestLog.init()` 后写同一个文件，同时镜像到 logcat（tag `tunvpn`）。

一次"测速全部"会留下（`testAll()` 清空每轮的去重键）：

```
=== 测速开始：N 个节点 · VPN=未连接 · 单目标超时 5s · 测速地址 ... · 内置目标 4 个 · 国家筛选=全部 ===
测速: 使用测试内核（跟随当前国家筛选）
测试内核配置：44 个代理条目 · 11520 字节 · 路径 .../coretest/config.yaml  ← 生成配置真带了几个代理

delay: 动作失败 code=-1 data=json: cannot unmarshal string into ... timeout of type int64 （参数被拒，换形状）
delay: 内核不接受参数形状#0（...）→ 试下一种 · 内核回 {"data":"invalid data type"}
delay: 采用参数形状#0（proxy-name/test-url/timeout=n）
delay: 可用 name=... 187ms shape#0 @http://...                             ← 每个测到的节点一行
delay: 动作失败 code=-1 data="proxy not exist" name=... url=... shape#0
测速: /proxies 映射里没有该节点，改用节点名直试 name=... addr=host:443     ← 按名字救回
测速: <内核里的代理名> @http://... -> 失败(-2) / 无判定（测试没跑起来）      ← 只记失败项
测速: <name> 救援探测成功 812ms @... / 判定不可用（所有目标与救援探测均失败）
测速结果: <节点名> [host:port ss] -> 不可用(-2)                            ← 每个不可用节点一行
=== 测速结束：可用 x / 不可用 y / 未测速 z ===
```

**`testDelay` 的参数形状（内核自己告诉我们的，别再猜）**：
1. 外层 `data` 必须是**参数字符串**，不能是内联对象，否则：
   `{"id":"","method":"testDelay","data":"invalid data type","code":-1}`
2. 字符串里 `timeout` 必须是**数字**（int64），传成字符串则：
   `json: cannot unmarshal string into Go struct field TestDelayParams.timeout of type int64`
3. 所以 `CoreTestHost.DELAY_SHAPES[0]` = `{"proxy-name":"...","test-url":"...","timeout":<int>}`（Go 端结构体名 `TestDelayParams` 已从报错里确认）。首个被内核接受的形状记在 `delayShape`，整轮复用；`ClashApiServer` 的 `/delay` 用 `CoreTestHost.delayData()` 保持同一形状。

> 判定口径之所以能保住，全靠 `TProxyService.apiActionRaw()` 拿到原始 `code`：`invalid data type` / `cannot unmarshal` / `json:` 开头的报错都说明"**参数被拒**"，不是节点判定，于是自动换下一种形状（日志：`delay: 动作失败 ...（参数被拒，换形状）`），绝不会因此把节点写成"不可用"。

**并发下的硬性约定（踩过的坑）**：桥的 `data` 容器（`dataAsString`）、`testDelay` 的参数形状（`delayShape`）、节点名映射（`proxyNameCache`）都是**一次性探测出来的共享闩锁**，必须在批量开始前用**单线程**定下来——`SubscribeActivity.delaySelfTest()` 在 `corePrepared` 置位之前跑一次并打 `测速自检：...`。否则 16 个并发探测会把这个闩锁竞争到错误值，然后整轮全部失败，表现为「**单个测速能用、测速全部全废**」。另外：只要本进程已有测试内核，就**不再回退**隧道内核的 REST（那是另一个节点池，只会多花一次往返并刷一屏 502）。

**进度条必须与"国别解析"解耦**：`testNode()` 里**先 `ui.post` 进度、再解析国别**。国别解析要 `InetAddress.getByName(域名)`，而它**没有超时**（坏 DNS / 域名不解析会卡几十秒）；原来顺序反了，第一个节点的进度就会在解析期间一动不动——表现为「进度一直 0%」。现在 `GeoIp.resolve()` 跑在自己的 4 线程池里、`Future.get(3s)` 到点即放弃（返回 null → UNKNOWN），进度只由探测结果驱动。`detectShape()` 也只要求"内核没拒绝参数"就定型（不等真实结果），否则 5 种形状 × 一个完整探测会把批量开始前就耗掉一分多钟。最后：`testAll()` 先把上一轮进度清零，筛选范围为空时给提示而非静默不动，并挂了 60 秒"零进展"看门狗日志。
> 另外：`getConnections` / `getProxies` / `startListener` 因为 `data` 为 null 一直是好的，所以"后台统计正常、一测速就全废"曾极难定位。

**节点如何在跑着的内核里被找到**（`realNodeName`）——两层，缺一不可：
1. **按名字**（`name:<节点名>`）：内核跑的是**我们自己生成的配置**，名字就是订阅名（含去重后缀），不会因为内核把 `server` 报成解析后的 IP 而对不上。
2. **按地址**（`server|port` 小写，再带协议类型兜底）：订阅里 `ss`/`vmess` 与内核报的 `Shadowsocks`/`Vmess` 拼写不同，所以地址键不带类型、类型键只作二级。
3. 两层都没命中时，**直接用订阅节点名发探测**（猜错只是一次失败探测，猜对就救回），同时打日志说明。

另有底层桥日志：`bridge: 动作 testDelay 等待 ...ms 未收到回调`（内核没响应）、`bridge: 动作 testDelay 返回 code=...`（内核报错，通常含 `proxy not exist`）、`clash-api delay: 内核判定失败(-1) name=...`。

**排查时把从 `=== 测速开始` 到 `=== 测速结束` 的整段贴出来即可**：它能区分「节点真死」与「测试没跑起来」。

> 判定链路的关键约定：`SubscribeActivity.noVerdict(nodeLevel)` 是**唯一的收口点**。
> - **节点级**无响应（探测已发出，在该节点时限内没有任何回包；或该节点的时限已用尽）→ 由 设置 → 订阅 → **「无响应判为不可用」**决定：**开（默认）= `-2`「不可用」**（这就是用户要的"超时即不可用"），关 = `-1`「未测速」（保守：只信内核的明确失败）。
> - **非节点级**（根本没探测：没有内核、节点不在内核配置里、本轮已被放弃）→ 一律 `-1`，绝不写成不可用。
> - 内核**明确**报失败（`504/408`，或动作返回负数）永远是 `-2`，与上面的开关无关。
> - 本轮"不可用"全部来自无响应时，收尾会写明"这是内核/桥异常而非节点全死"，并 Toast（`sub_test_all_timeout`）。
>
> **等待额度**：每次探测的等待 = `min(单目标超时+5s, 该节点剩余额度)`，同一额度也作为 `timeout` 交给内核。少了这一步「每节点测速上限」就是假的——5 秒的上限曾允许一次 9 秒探测，所以用户看到"设了没用"。

### 7.3 切换节点 / 国家的生效链路（"显示已切、实际没切"的修复）

**问题**：连接状态下换国家或点节点后，首页与通知栏立刻显示新名字，流量却仍走旧节点。

**根因**（三层脱节）：

| 环节 | 旧行为 | 后果 |
| --- | --- | --- |
| 国家筛选 | 只写 `SubCountryFilter` + Toast「重新连接后生效」 | 隧道节点池是**启动时烘焙进 `config.yaml`** 的（`MihomoConfig.mergedConfig`），运行中根本不会变 |
| 选中节点 | 只发 `ACTION_SELECT` → `PUT /proxies/tunvpn {"name":...}` | 该节点**不在运行配置的组里**时 PUT 失败（`proxy not exist`），失败只写日志，不切换 |
| 当前节点显示 | `getCurrentNode()` 纯由 `SubSelected` 派生 | 显示的是"愿望"，与内核实际选择的节点无关 → 首页/通知栏必然说谎 |

**修复**：

1. **`Preferences.ACTIVE_NODE`（运行时状态）**：`TProxyService.syncActiveNode()` 读 `GET /proxies/tunvpn` 的 `now` 并写入；`now` 是组时再往下钻（自动模式顶层是某个国家的 url-test 组，真正节点在他下面，最多 2 层）。`getCurrentNode()` 在**隧道已连接**时优先返回它，否则退回 `SubSelected`/SOCKS5。启动与断开时清空，避免残留。采样循环每 ~30 秒同步一次（自动模式下内核自己会换节点）。
2. **PUT 失败 → 自动重建配置**：`applySelector()` 拿到非 2xx 即认为"节点不在当前配置里"，调用 `rebuildForSelection()`（主线程 `rebuildTunnel()`）；仅对**用户主动选择**（`selectUserAction`）生效，60 秒去抖，自定义配置不重建（节点本就不在，重建无意义）。
3. **切换国家 → 立即重连**：`SubscribeActivity` 国家 chip 在已连接时直接发 `ACTION_RECONNECT`（该 action 即"重建配置并立即生效"，与 `AppListActivity` / `RulesHubActivity` 同一范式），不再让用户手动重连。

> 记住这条：**`config.yaml` 只在启动时生成**（订阅池、国家筛选、选中节点、代理端口、分流都在里面）。凡是"改了要生效"的设置，要么走 `ACTION_RECONNECT`，要么走 clash-api 的运行时接口（选择器）。只改 SharedPreferences = 只改了愿望。

## 8. 统计与通知

- 统计采样跑在 `HandlerThread("traffic-stats")`，每 1000ms 一次：
  - **实时 / 本次 / 累计**：来自 `Clash.INSTANCE.getTotalTraffic()`（内核累计总量，准确，独立于 9090）。
  - **代理专属流量 / 连接数**：`accumulateProxy()` 拉 `getConnections` 快照，只累加 `chains` 不是 `DIRECT` 的连接增量。

- 通知：标题 = 当前节点，正文 = 实时速率，展开为 节点 + 实时 + 本次 + 累计 + 「断开」。

## 9. 活跃连接 与 最近请求

### 活跃连接（`ConnectionsActivity`）

- **跨进程取数**：活动页在主进程，内核 / 桥 / 服务实例在 `:native`，所以它读的是 `:native` 每秒发布到 `SharedPreferences` 的**精简连接快照**（key `ConnSnapshot`，字段 `{t,r,p,u,d,s}`，上限 200，仅内容变化时写入）。每 1.5 秒**新建一个 `Preferences`** 重新读取（`MODE_MULTI_PROCESS` 需重新 `getSharedPreferences` 才刷新）。
- 每行展示：目标、`规则(内容) · 节点链`、来源应用、**`start` 转成的本地连接时间**、上下行。
- 「断开全部」→ `DELETE /connections`，在**后台线程**执行（桥调用会阻塞，不能在 UI 线程）。

### 最近请求（`RecentRequestsActivity`）

- 记录器在 `TProxyService`：`connInfo` 跟踪在途连接，某连接从快照消失即作为一条 `RecentRequest` 落库（`startMs/endMs` 用 `SystemClock.elapsedRealtime()`，目标 / 规则 / 链 / 进程 / 上下行），有上限、按流量排序，序列化到 `Preferences.getRecentRequests()`（字段 `t/r/c/p/u/d/s/e`）。
- 界面读取该 store；列表行含来源应用、**时长**与**请求时间**（开机相对时间换算成真实墙钟），点行看详情，「清空」同时清内存与持久化。
