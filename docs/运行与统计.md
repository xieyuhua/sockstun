# 运行与统计

本文是 [开发与架构](开发与架构.md) 的分支：隧道跑起来之后的那部分——统计采样、通知、活跃连接 / 最近请求、高频路径的性能约定、持久化结构与日志。

---

## 1. 统计与通知

统计采样跑在 `HandlerThread("traffic-stats")`，每 `STATS_INTERVAL` = **1000ms** 一次：

| 指标 | 来源 | 说明 |
| --- | --- | --- |
| **实时速率 / 本次 / 累计** | `Clash.INSTANCE.getTotalTraffic()`（JNI） | 内核累计总量，准确，独立于 9090 端口 |
| **代理专属流量 / 连接数** | `accumulateProxy()` 拉 `getConnections` 快照 | 只累加 `chains` 不是 `DIRECT` 的连接增量 |
| **分应用用量** | `StatsAppBase` / `StatsAppTotal` | 按 `metadata.process` 归类 |

- `accumulateProxy()` 每次成功取到快照后会缓存到 `connSnapshot`，供活跃连接页直接读取（见 §3）。
- 通知：标题 = 当前节点，正文 = 实时速率；展开为 节点 + 实时 + 本次 + 累计 + 「断开」。
- 首页 / 通知读取的是主进程里的 `SharedPreferences` 数字，刷新间隔 1.5s（`MainActivity.STATS_INTERVAL`），所以**服务端必须每秒写一次**——这是"降频"不能随便做的原因（见 §4）。

---

## 2. 连接快照的发布

`:native` 每秒把内核连接表压成一份**精简快照**发布到 `SocksStats`（key `connSnapshot`）：

- 字段 `{t,r,p,u,d,s}` = 目标 / 规则 / 进程 / 上行 / 下行 / 开始时间，上限 200 条；
- 只有内容变化时才写入（与上一次的 JSON 串比较）；
- 主进程读取时必须**新建 `Preferences`**（`MODE_MULTI_PROCESS` 下实例缓存不会自动刷新）。

---

## 3. 活跃连接 与 最近请求

### 3.1 活跃连接（`ConnectionsActivity`）

- **跨进程取数**：活动页在主进程，内核 / 桥 / 服务实例在 `:native`，所以它读的是 §2 的快照，每 1.5 秒重新读一次。
- 每行展示：目标、`规则(内容) · 节点链`、来源应用、`start` 转成的本地连接时间、上行 / 下行。
- **断开全部**：主进程调 `TProxyService.clearConnections(context, running)` —— 先本地清空 `connSnapshot`，再发 `ACTION_CLOSE_ALL_CONNS` intent，由 `:native` 在**采样线程**上 `closeAllConnections` 并清空去重缓存（`lastConnSnapshotJson` 复位，否则内容"没变化"就不会重写，旧列表会被内核立即重建的连接带回来）。
  - 不能由主进程直接发 HTTP：`MihomoConfig.API_PORT` 是每进程一份的静态值，主进程恒为 9090，而 `:native` 的 `pickApiPort()` 可能选到 9091+（实际端口由 `Preferences.getApiPortActual()` 提供）。

### 3.2 最近请求（`RecentRequestsActivity`）

- 记录器在 `TProxyService`：`connInfo` 跟踪在途连接，某连接从快照消失即作为一条 `RecentRequest` 落库（`startMs/endMs` 用 `SystemClock.elapsedRealtime()`；字段 `t/r/c/p/u/d/s/e`），有上限、按流量排序，序列化到 `Preferences.getRecentRequests()`。
- 时间由服务在**落盘时**换算成墙钟（`ws` 字段）：开机毫秒数跨重启没有意义，旧格式记录换算会跑到未来日期，这类记录的时刻显示为空。
- **清空**：`TProxyService.clearRecentRequests(context, running)` —— 先清本进程持久化副本，再发 `ACTION_CLEAR_RECENT`，由 `:native` 在采样线程上**三处一起清**（内存列表 + `connInfo` + 持久化），否则下一拍 `flushRecentRequests()` 会把旧内存数据全量写回（"清了又回来"）。`connSeen` 刻意保留：它只用于流量增量，清掉会把已传输的字节重新计一遍。
- 即使当前列表为空也允许点「清空」（解析失败或持久化里留着旧数据时，提前 return 会让操作看起来没反应）。

## 4. 高频路径的性能约定（改这些地方前先读）

主进程只能通过 `SharedPreferences` 看到 `:native` 的数字，所以"降频"不是随便能做的优化；下面几条是权衡后的结论：

| 位置 | 约定 | 原因 |
| --- | --- | --- |
| 每秒统计 | ① 两组计数用**一次** `Preferences.setAllStats()`（一个 editor/commit）；② 统计类读写**全部走 `SocksStats` 独立文件**（`PREFS_STATS_NAME`） | 每秒一次是**必须**的（首页/通知的实时速率靠它跨进程刷新）。分两次 commit = 两次整文件写入，还会出现"隧道数已更新、代理数还是旧值"的撕裂；而主文件 `SocksPrefs` 里还存着几百 KB 的订阅原文 / 节点 JSON —— 不拆文件的话，每秒的 commit 都要把这么大的 XML 重写 + fsync |
| 增量保存节点缓存 | `saveNodes()` **单趟**按 `subId` 分桶，再用 `Preferences.setSubNodesAll()` **一次 commit** | 一轮测速每 15 个节点存一次；逐份订阅各扫一遍 + 各 commit 一次会反复重写含大 blob 的主文件 |
| 国别映射 `ServerCountryMap` | 内存缓存 + 写入**合并到每 ~2s 一次**，一轮测速结束 `flushCountryMap()` 收尾 | 配置生成对每个节点都调 `getServerCountry()`，不缓存就是 O(n²) 次 JSON 解析 + 整文件 commit |
| `ClashParser` | `LINE_BREAK` 预编译；`tryBase64` 用逐字符扫描代替 `String.matches()` | `matches()` 每次调用都编译正则，而订阅体有几百 KB |
| `ClashApiServer` worker | **4**（原 16） | 所有路由最终都落到单回调的 `apiAction()`，再多 worker 也只是排队等同一把锁（16 个 ≈ 16MB 栈，零吞吐收益） |
| 长循环后台线程 | 必须检查 `tunnelStopping`：选择器重试（≤6min）、`verifyController`（≤120s）、`testProxyConnectivity`（≤40 次）、延迟 3s 的 `kickClashApi` | 否则断开隧道后它们还会跑几分钟，既拖住 Service 不能回收，又在操作已释放的资源 |
| 节点行 `getView()` | 必须用 `Row`（ViewHolder）缓存 9 个子 View；点击监听器**只建一次**（节点挂在按钮 tag 上）；选中节点名缓存在 adapter，`notifyDataSetChanged()` 时刷新 | 测速期间每 400ms 就全量重绑一次，旧写法每行做 9 次 `findViewById`、new 2 个监听器、读一次 preferences |
| 时间格式化 | `SimpleDateFormat` 一律 **ThreadLocal 复用**（`TestLog.TS`、`ConnectionsActivity.CONN_IN_*`、`RecentRequestsActivity.CLOCK_FMT`） | 构造昂贵且非线程安全；连接页 200 行每秒整体刷新，旧写法每秒产生几百个格式化器 |
| `TProxyService.formatBytes()` | 手写定点格式化，**不要用 `String.format`**；小数位：值 < 10 保留两位，否则一位 | 通知栏与首页每秒各调用十几次；该函数在统计线程与 UI 线程都会被调，注意保持输出格式不变 |
| 通知栏重建 | 两个 `PendingIntent` 缓存复用；`updateNotification()` 把已算好的实时行传给 `buildNotification(line)` | 通知每秒重建；`PendingIntent.getActivity/getService` 每次都要跨 Binder，而内容从不变化 |
| 正则 | 不在**循环内**编译：`SubscribeActivity.findRawProxyIn()` 的两个 `Pattern` 提到循环外；`GeoIp` 用 `isDottedQuad()`/`isAlpha2()` 手写扫描 | `matches()` / `Pattern.compile` 的编译开销远大于匹配本身，而这些点都是"每个节点一次" |

> **已知但有意保留的热点**（收益大、改动面也大，动之前先评估）：
> - `TestLog` 目前**每写一行就 open/close 一次文件**；批量测速下失败节点会逐行写。改成常驻 `BufferedWriter` + 定时 flush 能省掉大部分 syscall，代价是进程被杀时可能丢最后几行。注意时间戳格式化已 ThreadLocal 化，单行开销已在微秒量级，优先级不高。
> - `publishConnSnapshot()` 每秒重建整份 JSON（上限 200 条）再与上一次比较：量级在微秒/秒，比较本身已经挡住了真正的成本（`SharedPreferences` 写入），所以**有意保留**。
> - `MihomoConfig` 生成一次隧道配置只解析自己的节点文本**一次**：`mergedConfig()` 把写出去的 `proxies:` 段解析回来用于建组，并在同一处记下节点数（`lastBuiltNodes`，`describe()` 的日志行 `routing: N node(s)` 用它）。这取代了以前"重新解析每份订阅来数节点"的做法——那种数法把国家筛选掉、内核拒绝掉的节点也算在内。

## 5. 持久化

### 5.1 两个 `SharedPreferences` 文件

`Preferences` 同时持有两个：

| 文件 | 内容 | 分档 |
| --- | --- | --- |
| `SocksPrefs`（`PREFS_NAME`） | 配置、订阅、规则、服务器等 | **按配置档隔离**，key 前缀 `P<index>.` |
| `SocksStats`（`PREFS_STATS_NAME`） | 高频写入的统计、连接快照、最近请求、实际端口 | 全局，不分档 |

拆分原因见 §4。`migrateStats()` 会一次性把旧文件里的统计搬过来并删掉旧键（只在"新文件还没有统计"时执行），**key 名与旧版完全一致**。

### 5.2 配置档

- `Selected` 当前档，`ProfileCount` 数量（上限 `MAX_PROFILES` = 13）；新增 = 复制当前档，删除 = 后续下标平移。
- 首次启动把旧的扁平 key 迁进第 0 档（`Preferences.migrate()`）。
- **界面现状**：当前没有配置档切换 / 新增 / 重命名入口，实际只有第 0 档在用；底层能力保留，接回 UI 时无需改存储层。

### 5.3 主要 key

| Key | 文件 | 含义 |
| --- | --- | --- |
| `Subscriptions` / `SubActive` | SocksPrefs | 订阅列表（JSON）/ 当前启用订阅 id |
| `SubRaw.<id>` / `SubNodes.<id>` | SocksPrefs | 每个订阅的原文 / 节点缓存（JSON） |
| `SubSelected` / `SubCountryFilter` / `SubProtoFilter` | SocksPrefs | 选中节点名 / 国家筛选 / 协议筛选 |
| `ActiveNode` | SocksPrefs | 内核**当前真正在用**的节点（运行时事实） |
| `SocksServers` / `SocksActive` / `ServerBackups` | SocksPrefs | 手动服务器列表 / 启用的那台 id / 服务器备份 |
| `AutoSelect` / `AutoSelectInterval` / `AutoTestUrl` / `AutoSelectCountry` | SocksPrefs | 自动选择开关 / 间隔 / 测试地址 / 目标国家组 |
| `ProxyTestTimeout` / `ProbeTimeoutAsFail` / `PreloadCore` / `ShowUnavailable` | SocksPrefs | 延迟测试超时 / 无响应判不可用 / 未连接时预加载内核 / 显示不可用节点 |
| `ProxyPort` / `AllowLan` | SocksPrefs | 混合端口 / 局域网代理 |
| `Rules` / `RulesStrategy` / `RulesDefaultProxy` | SocksPrefs | 规则列表 / 分流策略 / 未命中默认 |
| `Global` / `Apps` / `UdpInTcp` | SocksPrefs | 作用域模式（默认全局）/ 部分应用白名单 / UDP relay over TCP |
| `DnsIpv4` / `DnsIpv6` / `RemoteDNS` / `Ipv4` / `Ipv6` | SocksPrefs | DNS 与隧道协议 |
| `WebdavEnabled` / `WebdavUrl` / `WebdavUser` / `WebdavPass` / `WebdavDir` | SocksPrefs | WebDAV 远程备份 |
| `ApiSecret` | SocksPrefs | clash-api 令牌 |
| `ApiPortActual` | **SocksStats** | `:native` 实际选中的 clash-api 端口（主进程据此发请求） |
| `Stats*` / `Proxy*` / `StatsApp*` | SocksStats | 流量统计（总 / 本次 / 速率 / 代理专属 / 分应用） |
| `connSnapshot` / `recentRequests` | SocksStats | 连接快照 / 最近请求 |
| `Enable` / `LastError` | SocksPrefs | 连接状态 / 上次失败原因 |

> 运行时全局值（`ApiPortActual`）刻意**不**带配置档前缀。

## 6. 日志

- 开关 `LogEnabled`（默认开），**下次连接生效**。
- 落盘 `cache/tproxy.log`（应用私有目录），内核日志经 `setEventListener` 一并写入；内核自身的 `log.file` 指向 `cache/mihomo.log`。
- 启动阶段的致命错误用 `appendLog()` 直写文件，不受开关影响。
- 批量测速期间日志会降量（成功探测不逐行写），排查方式见 [订阅与测速](订阅与测速.md) §6。
