# tunVPN 内核接口（mihomo external-controller）说明

内嵌内核是 **mihomo（Clash.Meta） v1.19.30**，它自带一套 RESTful API（俗称 external-controller / Clash API）。
App 自己解析订阅 YAML、自己 TCP 测速、自己数流量，其实**这些数据内核都算好了**，直接问内核更准也更省事。

本文档说明：

- 怎么访问这套 API（含 PC 上调试的办法）；
- 内核总共有哪些接口、各自能看到什么数据；
- 每个数据源对这个 App 有什么价值、**当前接了没有**；
- 值得接入的优先级、实现要点和已知的坑。

> 参考：[mihomo APIs 官方文档](https://wiki.metacubex.one/api/)（本文按其 v1.19 时代的分组整理）。

---

## 1. 怎么访问

### 1.1 地址与认证

接口监听在**设备本机的回环地址**，由 `MihomoConfig.build()` 在配置里注入：

```yaml
external-controller: 127.0.0.1:9090
```

| 项目 | 当前值 | 说明 |
| --- | --- | --- |
| 地址 | `127.0.0.1:9090` | 见 `MihomoConfig.API_PORT` |
| 认证 | **无**（没设 `secret`） | 回环地址，外部网络到不了 |
| 前缀 | 无 | 直接用 `http://127.0.0.1:9090/xxx` |

若将来要设密钥，配置里加 `secret: <token>`，则每个请求都要带：

```
Authorization: Bearer <token>
```

`external-controller` 这一行只在订阅/YAML 里**没有**的时候才由 App 追加，也就是说：**如果订阅自己写了 `external-controller`，用的是订阅那一份**（可能是别的端口、别的地址，甚至带 secret）。排查接口读不到数据时，先确认内核实际用的地址。

> 安全提醒：`127.0.0.1` 意味着**只有本机能访问**，跟 `allow-lan` 无关（回环地址本来就不受 allow-lan 影响）。这套 API 会把每条连接的目标域名吐出来，绝不能改成 `0.0.0.0` 或加 `allow-lan`。

### 1.2 在 PC 上调试（很实用）

设备上的 `127.0.0.1` 从 PC 直接 curl 是连不上的，用 adb 端口转发：

```bash
adb forward tcp:9090 tcp:9090

curl -s http://127.0.0.1:9090/version
curl -s http://127.0.0.1:9090/connections
curl -s http://127.0.0.1:9090/proxies
```

隧道跑起来的前提下，这样可以直接看真实返回，比在 App 里加日志快得多。

### 1.3 两种交互模式

**（a）一次性请求** —— 普通 HTTP，返回一份 JSON 快照。

```
GET /proxies        → 完整节点列表 + 延迟历史
GET /configs        → 当前运行配置
```

**（b）流式推送** —— `/traffic`、`/logs`、`/memory`、`/connections` 这四个支持实时推送，两种连法：

1. **WebSocket**：请求头带 `Upgrade: websocket`。面板（yacd / metacubexd）走这条。
2. **分块流（chunked）**：**不带** Upgrade 头直接 GET。内核会保持连接，把 JSON 对象**一个接一个连续写出来**（对象之间没有分隔符）。

第 2 种对 Android 意义很大：`HttpURLConnection.getInputStream()` 读下去就行，**不需要实现 WebSocket 协议**（Java 标准库没有 WS 客户端，手写握手+解帧要上百行）。代价是拿到的是一串粘连的 JSON，得自己按花括号配对切分。

### 1.4 当前 App 的接入方式

只有一个地方在走 HTTP：

| 位置 | 用途 | 频率 |
| --- | --- | --- |
| `TProxyService.accumulateProxy()` | 拉 `/connections`，把 `chains` 不是 `DIRECT` 的连接的上传/下载增量累加，得到「经代理的流量」 | 每秒 1 次 |
| `ConnectionsActivity.fetch()` | 拉 `/connections`，画活跃连接列表 | 可见时 1.5 秒 1 次 |

另外 `TProxyService` 里通过 **JNI** 拿了两样东西（不走 HTTP）：

```java
Clash.INSTANCE.getTraffic();        // {"up":..,"down":..}
Clash.INSTANCE.getTotalTraffic();   // 累计总量
```

也就是说：**内核暴露了 40 多个端点，App 目前只用了 1 个。**

- 下面所有 JSON 都是**字段示例**，以实际返回为准（不同版本会多字段）。

## 3. 数据详解

### 3.1 流量：`/traffic`

最干净的一路数据 —— 内核自己算好的收发速率与累计值。

**请求**：`GET /traffic`（流式，每秒推一次）

```json
{"up": 12340, "down": 567890, "upTotal": 1048576, "downTotal": 20971520}
```

| 字段 | 含义 | 单位 |
| --- | --- | --- |
| `up` | 当前上传速率 | **字节/秒** |
| `down` | 当前下载速率 | **字节/秒** |
| `upTotal` | 本次内核启动以来的上传总量 | 字节 |
| `downTotal` | 本次内核启动以来的下载总量 | 字节 |

**⚠️ 关键区别**：`up` / `down` 是**速率**，不是累计值；累计值叫 `upTotal` / `downTotal`。
`TProxyService.jsonBytes()` 的兜底分支把 `getTraffic()` 的 `up`/`down` 当成累计值用（见 §6.1），这里的语义差异就是那个隐患的来源。

**对 App 的价值**：
- 首页/通知里的实时速率，可以不再靠「两次采样求差」自己算，内核直接给；
- `upTotal`/`downTotal` 是**内核视角的全部流量**（含直连），可以作为「本次连接总量」的基准。

**注意**：这是「内核处理的一切流量」，**不区分代理和直连**。想知道有多少真的走了节点，还得看 `/connections` 的 `chains`（这正是 App 现在干的事）。

### 3.2 连接表：`/connections`

App 已经用了，但只用了其中一部分字段。

**请求**：`GET /connections`（快照）
流式：`GET /connections?interval=1000`（毫秒，默认 1000）

```json
{
  "downloadTotal": 20971520,
  "uploadTotal": 1048576,
  "memory": 12345678,
  "connections": [
    {
      "id": "8f3c1a2e-...",
      "metadata": {
        "network": "tcp",
        "type": "HTTP",
        "sourceIP": "172.19.0.2",
        "destinationIP": "142.250.66.100",
        "sourcePort": "41234",
        "destinationPort": "443",
        "host": "www.google.com",
        "dnsMode": "fake-ip",
        "uid": 10123,
        "process": "com.android.chrome",
        "processPath": "/data/app/~~xxx/base.apk",
        "specialProxy": "",
        "specialRules": "",
        "remoteDestination": "",
        "dscp": 0,
        "sniffHost": ""
      },
      "upload": 1234,
      "download": 56789,
      "start": "2026-09-11T10:00:00.123456789+08:00",
      "chains": ["香港 01"],
      "providerChains": ["机场A"],
      "rule": "DomainSuffix",
      "rulePayload": "google.com"
    }
  ]
}
```

**顶层字段**

| 字段 | 含义 |
| --- | --- |
| `downloadTotal` / `uploadTotal` | 内核累计收发（与 `/traffic` 的 total 同源） |
| `memory` | 内核当前内存占用（字节） |
| `connections` | 当前所有活跃连接 |

**单条连接字段**

| 字段 | 含义 | 为什么有用 |
| --- | --- | --- |
| `id` | 连接唯一 ID | 用来单独关闭（`DELETE /connections/{id}`），或做增量统计的 key |
| `metadata.host` | 目标域名（嗅探/fake-ip 得到） | 比 IP 更有可读性 |
| `metadata.destinationIP` / `destinationPort` | 目标 IP 与端口 | `host` 为空时兜底 |
| `metadata.sourceIP` / `sourcePort` | 来源（TUN 内部地址） | 基本没用 |
| `metadata.network` | `tcp` / `udp` | UDP 太多时常是 QUIC，可用来解释流量分布 |
| `metadata.type` | 入站类型（`HTTP` / `SOCKS` / `TUN`） | 区分是走混合端口还是 TUN |
| `metadata.process` / `uid` | 发起连接的应用包名 / UID | **可以做「哪个 App 在跑流量」**，比 App 自己统计准 |
| `metadata.dnsMode` | `fake-ip` / `normal` 等 | 排查 DNS 问题 |
| `metadata.sniffHost` | 嗅探出的域名 | `host` 不准时的补充 |
| `metadata.specialProxy` / `specialRules` | 被特殊规则强制的代理/规则 | 排查「为什么这条没按规则走」 |
| `upload` / `download` | **这条连接**累计收发 | 当前排序列的依据 |
| `start` | 连接建立时间 | 能看出长连接活了多久 |
| `chains` | **出口链路**（节点名数组） | `["DIRECT"]` = 直连；`["香港 01"]` = 走了节点 |
| `providerChains` | 节点来自哪个 provider | 多订阅合并时能看出节点归属 |
| `rule` / `rulePayload` | 命中的规则类型与内容 | **验证 App 的规则页到底有没有生效** |

**关闭连接**：

```
DELETE /connections        → 关闭全部（204）
DELETE /connections/{id}   → 关闭一条（204）
```

**对 App 的价值**：
- 已在用：`chains` 判断代理/直连，累加代理流量；活跃连接页。
- **可挖掘**：`metadata.process` → 「本次会话各 App 走了多少代理流量」；`rule`/`rulePayload` → 规则页显示真实命中；`DELETE` → 加一个「断开全部连接」按钮（不重连隧道，只掐现有连接）。

### 3.3 节点：`/proxies`

**这是信息量最大的一个接口。** App 现在靠自己解析订阅 YAML + 自己 TCP 测速拿节点列表，其实内核已经把合并后的**最终节点池**和**真实延迟历史**都摆好了。

**请求**：`GET /proxies`

```json
{
  "proxies": {
    "DIRECT": {
      "name": "DIRECT", "type": "Direct", "alive": true,
      "udp": true, "xudp": false, "tfo": false, "mptcp": false, "smux": false,
      "history": []
    },
    "香港 01": {
      "name": "香港 01", "type": "Shadowsocks", "alive": true,
      "udp": true, "xudp": false, "tfo": false, "mptcp": false, "smux": false,
      "history": [{ "time": "2026-09-11T10:00:00+08:00", "delay": 123 }],
      "provider-name": "机场A"
    },
    "tunvpn": {
      "name": "tunvpn", "type": "URLTest", "alive": true,
      "udp": true, "xudp": false, "tfo": false, "mptcp": false, "smux": false,
      "history": [],
      "now": "香港 01",
      "all": ["香港 01", "日本 02", "DIRECT"],
      "testUrl": "http://www.gstatic.com/generate_204",
      "expectedStatus": "204",
      "fixed": "",
      "interval": 300,
      "tolerance": 50,
      "lazy": false,
      "hidden": false,
      "icon": ""
    }
  }
}
```

**普通节点字段**

| 字段 | 含义 |
| --- | --- |
| `name` / `type` | 节点名 / 协议类型（`Shadowsocks`、`Vmess`、`Trojan`、`Hysteria2`、`Vless`…） |
| `alive` | 最近一次测速是否成功 |
| `history` | **延迟历史数组**，元素 `{time, delay}`（毫秒，`0` 或缺失代表超时） |
| `udp` / `xudp` / `uot` | 是否支持 UDP / XUDP / UDP over TCP |
| `tfo` / `mptcp` / `smux` | 性能开关状态 |
| `interface` / `routing-mark` | 绑定网卡 / 路由标记（本 App 不用） |
| `provider-name` | 来自哪个代理集合（订阅） |
| `dialer-proxy` | 底层拨号节点（链式代理） |
| `extra` | 按测试 URL 分组的额外延迟历史 |

**策略组（Selector / URLTest / Fallback / LoadBalance）额外字段**

| 字段 | 含义 |
| --- | --- |
| `now` | **当前选中的节点名**（LoadBalance 没有） |
| `all` | 组内所有成员（数组） |
| `testUrl` | 测速用的 URL |
| `expectedStatus` | 期望的 HTTP 状态码（Selector 没有） |
| `fixed` | 被手动固定的选择（仅 URLTest / Fallback） |
| `interval` / `tolerance` / `lazy` | 自动测速的间隔、抖动容差、惰性模式 |
| `hidden` / `icon` | 面板展示用 |

**读单个 / 切换 / 清除固定**：

```
GET    /proxies/{name}          → 单个对象（格式同上）
PUT    /proxies/{name}          → body {"name":"日本 02"}，切换到该节点（204）
DELETE /proxies/{name}          → 清除 fixed 固定选择（204，Selector 无效）
```

**读延迟**：

```
GET /proxies/{name}/delay?url=http://www.gstatic.com/generate_204&timeout=5000
→ 成功 {"delay": 123}
→ 失败 HTTP 504 {"message": "An error occurred in the delay test"}
```

可选 `?expected=204`（期望状态码，支持 `200/204`、`200-299` 区间写法）。

**对 App 的价值（很高）**：
1. **当前选中节点**：`GET /proxies/tunvpn` 的 `now` 字段 —— 比 App 自己记「用户选了谁」更可靠，因为 url-test 模式下是**内核在切换**，App 原本无从得知；
2. **真实延迟**：`history` 是内核按 `interval` 实测的结果，`/proxies/{name}/delay` 是一次按需实测 —— 两者都是**通过真实代理协议握手测的**，比 App 层对 `server:port` 做 TCP connect 准得多（节点端口可能通但协议认证失败）；
3. **节点列表**：多订阅合并后内核认可的最终名单，含 `alive` 状态，可以直接替代 `ClashParser` 的解析结果用来展示（但**不能替代**配置生成 —— 配置还是要自己拼，见 §6.3）；
4. **切换节点**：与 JNI 的 `Clash.INSTANCE.invokeAction()` 等价，二选一即可。

### 3.4 代理集合：`/providers/proxies`

**订阅的元信息（流量、到期时间）就在这里。** 订阅响应头里的 `subscription-userinfo`，内核已经解析好放在 provider 对象里了。

**请求**：`GET /providers/proxies`

```json
{
  "providers": {
    "机场A": {
      "name": "机场A",
      "type": "Proxy",
      "vehicleType": "HTTP",
      "updatedAt": "2026-09-11T10:00:00+08:00",
      "subscriptionInfo": {
        "Upload": 123456789,
        "Download": 987654321,
        "Total": 107374182400,
        "Expire": 1798761600
      }
    }
  }
}
```

| 字段 | 含义 |
| --- | --- |
| `vehicleType` | 拉取方式（`HTTP` / `File` / `Compatible`） |
| `updatedAt` | **上次更新时间**（可以用来展示「订阅多久没更新了」） |
| `subscriptionInfo.Upload` | 已用上传（字节） |
| `subscriptionInfo.Download` | 已用下载（字节） |
| `subscriptionInfo.Total` | 套餐总量（字节，可能为 0 = 不限量） |
| `subscriptionInfo.Expire` | **到期时间（Unix 秒）** |

**读单个 / 更新 / 健康检查**：

```
GET  /providers/proxies/{name}                  → 含完整 proxies 列表（对象，非数组）
PUT  /providers/proxies/{name}                  → 立即重新拉取订阅（204）
GET  /providers/proxies/{name}/healthcheck      → 触发全员健康检查（204）
GET  /providers/proxies/{name}/{proxy}          → 集合内单个节点
GET  /providers/proxies/{name}/{proxy}/healthcheck?url=&timeout=  → 单节点测速
```

**对 App 的价值（最高）**：
- **剩余流量 / 到期时间** —— 现在订阅页完全没有这些信息，而这是用户最关心的。内核已经解析好了，读一次就能展示；
- **`updatedAt`** —— 判断订阅是否拉取成功、多久没更新；
- **`PUT` 更新** —— 可以让「拉取订阅」变成「先落盘原始 YAML → 让内核重载」，避免两套解析逻辑。

> ⚠️ 前提：`subscription-userinfo` 是**订阅服务器**在响应头里给的。机场不给，这里就是空的。字段名首字母大写（Go 的 JSON 序列化结果），解析时注意大小写。
> 另外 `subscriptionInfo` 不是所有内核版本都有，代码里要当可选字段处理。

### 3.5 规则：`/rules`

**能看到内核实际加载的规则，以及每条规则命中了多少次。** 这是验证「规则页到底生效没有」最直接的证据。

**请求**：`GET /rules`

```json
{
  "rules": [
    {
      "index": 0,
      "type": "DomainSuffix",
      "payload": "github.com",
      "proxy": "tunvpn",
      "size": -1,
      "extra": {
        "disabled": false,
        "hitCount": 12,
        "hitAt": "2026-09-11T10:01:02+08:00",
        "missCount": 3,
        "missAt": "2026-09-11T10:00:58+08:00"
      }
    },
    { "index": 1, "type": "IPCIDR", "payload": "1.2.3.0/24", "proxy": "DIRECT", "size": -1 },
    { "index": 2, "type": "Match", "payload": "", "proxy": "tunvpn", "size": -1 }
  ]
}
```

| 字段 | 含义 |
| --- | --- |
| `index` | 规则序号（0 起，**就是匹配优先级**） |
| `type` | `DomainSuffix` / `IPCIDR` / `GeoIP` / `Match` … |
| `payload` | 规则内容（`Match` 为空） |
| `proxy` | 命中后走谁（`DIRECT` / `REJECT` / 组名） |
| `size` | 仅 `GeoIP` / `GeoSite` 有意义，其余 `-1` |
| `extra` | 命中统计（较新版本才有）：`hitCount` / `hitAt` / `missCount` / `missAt` / `disabled` |

**临时禁用规则**：

```
PATCH /rules/disable
body: {"0": false, "1": true}     // key = 规则 index，value = 是否禁用
→ 204
```

> 重启内核后失效。

**对 App 的价值**：
- 规则页可以显示「内核里实际是第几条」，和用户配的顺序对得上；
- `hitCount` 能回答「我加的这条规则到底有没有被用到」；
- **`Match` 那条的 `proxy` 字段 = 所有未命中流量的去向** —— 直连还是走代理，一眼可见（这正是之前排查「没流量」时最需要的那个信息）。

### 3.6 运行配置与版本：`/configs`、`/version`、`/configs/geo`

**`GET /version`**

```json
{"meta": true, "version": "v1.19.30"}
```

`meta: true` 是 Meta 内核的标识。**可以显示在「关于」里，比在 build.gradle 里硬编码版本号可靠**。

```
PATCH /configs

→ 204
```

**`PUT /configs?force=true`** 重载配置（body `{"path":"", "payload":""}`）—— 想让内核重新读 `config.yaml` 时用。

**对 App 的价值（高，而且被低估）**：
- **配置自检**：启动后读一次 `/configs`，确认 `tun.enable`、`mixed-port`、`dns.enable` 真的是期望的值 —— 比「日志里说要写 dns 段」直接得多；
- **`mode` 字段**：`rule` / `global` / `direct`。如果哪天「连上了但全部直连」，先看这里是不是被切成了 `direct`；
- **`Match` 规则 + `mode` 一起看**，基本能定位所有「没走代理」的问题。

### 3.7 日志与内存：`/logs`、`/memory`

**`GET /logs`**（流式）

```
GET /logs?level=info              → {"type":"info","payload":"[TCP] xxx --> yyy match DomainSuffix(x) using 香港 01"}
GET /logs?level=debug&format=structured
```

结构化模式下字段为 `time` / `level` / `message` / `fields`。

| `type` 取值 | 含义 |
| --- | --- |
| `debug` / `info` / `warning` / `error` | 日志级别 |

**对 App 的价值**：App 现在通过 `setEventListener`（JNI）拿内核日志写文件，**和这个接口是同一份数据**。如果哪天想在内核跑起来的**任意时刻**改日志级别（比如「开启详细日志」开关），`?level=debug` 重新连一次就行，不用改配置重启。

**`GET /memory`**（流式，每秒）

```json
{"inuse": 12345678, "oslimit": 0}
```

`inuse` = 内核当前堆占用（字节）。**对 App 的价值**：设置页可以显示「内核内存占用」，排查长时间运行后的内存增长。注意这是 **Go 堆**，不是整个进程（`libmihomo.so` 的 native 内存不含在内）。

### 3.8 缓存与维护

| 接口 | 方法 | 作用 | 什么时候用 |
| --- | --- | --- | --- |
| `/cache/dns/flush` | POST | 清 DNS 缓存 | 改了 DNS 设置后，不想重连隧道 |
| `/cache/fakeip/flush` | POST | 清 fake-ip 缓存 | 域名解析串味、App 拿不到新 IP 时 |
| `/restart` | POST | 重启内核 | 比杀进程优雅；但本 App 的 TUN 是外部传 fd 的，重启内核会**丢掉 TUN**，慎用 |
| `/dns/query?name=x&type=A` | GET | 用内核的解析器查一次域名 | 做个「DNS 诊断」入口，看 fake-ip / 真实 IP 走向 |
| `/storage/{key}` | GET/PUT/DELETE | 内核自带的键值存储（≤1MB，值必须是合法 JSON） | 基本用不上，App 自己有 SharedPreferences |
| `/upgrade`、`/upgrade/ui`、`/upgrade/geo` | POST | 内核/面板/GEO 自升级 | **Android 内嵌场景不适用**（内核编译进 .so，无法自替换） |
| `/debug/gc` | PUT | 触发一次 GC | 需要内核以 `log-level: debug` 启动 |
| `/debug/pprof` | 浏览器 | 内存/分配剖析 | 开发期排查内存问题，需 debug 级别 |

**`/dns/query` 响应**：

```json
{
  "Status": 0,
  "Question": [{ "name": "www.google.com.", "Qtype": 1, "Qclass": 1 }],
  "Answer": [{ "name": "www.google.com.", "TTL": 300, "IP": "1.2.3.4" }],
  "TC": false, "RD": true, "RA": true, "AD": false, "CD": false
}
```

**`/group` 系列**（`/group`、`/group/{name}`、`/group/{name}/delay`）是**旧接口**，等价于 `/proxies` 里 `type` 是 `Selector` / `URLTest` / `Fallback` / `LoadBalance` 的那些项。新代码直接用 `/proxies`。

## 5. 值得接入的（按优先级）

### P0 · 订阅流量与到期时间（`/providers/proxies`）

用户在订阅页最想看的两件事，现在都没有。

```java
String body = httpGet("http://127.0.0.1:" + MihomoConfig.API_PORT + "/providers/proxies");
JSONObject providers = new JSONObject(body).optJSONObject("providers");
for (Iterator<String> it = providers.keys(); it.hasNext(); ) {
    JSONObject p = providers.optJSONObject(it.next());
    JSONObject info = p.optJSONObject("subscriptionInfo");   // 可能为 null
    if (info == null) continue;
    long used  = info.optLong("Upload") + info.optLong("Download");
    long total = info.optLong("Total");        // 0 = 不限量
    long expire = info.optLong("Expire");      // Unix 秒
}
```

要点：

- **必须在隧道运行时才有值**（内核在跑才有 provider）；
- provider 的 key 是**配置文件里的名字**，本 App 是自己拼配置，所以需要给每个订阅生成一个可预期的 provider 名，才能和 App 里的订阅一一对应；
- `Total == 0` 要显示成「不限量」而不是 `0 B`；
- `Expire == 0` 表示永不过期。

> ⚠️ 这一项有个**前置改造**：现在的配置是「把订阅原文拼成一份 `proxies:` 列表」，**没有用 `proxy-providers`**，所以内核里**根本没有 provider 对象**，这个接口会是空的。要拿到 `subscriptionInfo`，得改成用 `proxy-providers` 挂载每个订阅。这是个结构性改动，收益也最大（顺带能天然支持「多订阅各自独立更新」）。

### P1 · 当前选中节点（`/proxies/{GROUP}`）

```java
JSONObject g = new JSONObject(httpGet("http://127.0.0.1:" + MihomoConfig.API_PORT
        + "/proxies/" + urlEncode(MihomoConfig.GROUP)));
String now = g.optString("now");
```

打开自动选择（url-test）后，**真正在用的节点是内核挑的**，App 只能靠 `/connections` 的 `chains` 反推，或者像现在这样显示「用户选的那个」——两者会不一致。有了 `now` 就能显示「当前实际出口」。

首页/通知里的节点名建议都以这个为准。

### P2 · 用内核测速替代自测（`/proxies/{name}/delay`）

```
GET /proxies/{name}/delay?url=http://www.gstatic.com/generate_204&timeout=5000
```

优势是**走真实节点协议**：只做 TCP connect 的话，一个「端口开着但密码错」的节点会被判成可用，内核测速不会。

```java
// 504 = 超时/不可用；200 才有 delay
```

并发测速要自己限流（别几百个一起上）。失败时的 `{"message": "..."}` 比 App 现在的「超时」更有信息量。

### P3 · 轻量收尾

- **活跃连接页加「断开全部」** → `DELETE /connections`；
- **「关于」显示内核真实版本** → `/version` 的 `version`；
- **规则页显示命中次数** → `/rules` 的 `extra.hitCount`（顺便验证规则有没有生效）；
- **启动自检** → 读一次 `/configs`，把 `mode` / `tun.enable` / `mixed-port` 写进日志，`mode` 不是 `rule` 就直接告警（这是「连上但全直连」的常见原因）。

## 6. 坑与注意事项

### 6.1 `/traffic` 的 `up`/`down` 是速率不是总量

内核的两个口径：

| 接口 / 字段 | 含义 |
| --- | --- |
| `/traffic` 的 `up` / `down` | **速率**（字节/秒） |
| `/traffic` 的 `upTotal` / `downTotal` | 累计（字节） |
| `/connections` 的 `uploadTotal` / `downloadTotal` | 累计（字节） |
| `/connections` 单条的 `upload` / `download` | 该连接累计（字节） |

`TProxyService.jsonBytes()` 的兜底链是 `{"downloadTotal", "down", "Download"}` —— 当主接口拿不到、退到 JNI `getTraffic()` 时，取到的 `up`/`down` 是**每秒速率**却被当作累计值存进 `sessionTx`/`sessionRx`。表现是流量总数会明显偏小且不稳定。
主路径（`getTotalTraffic()` 带的 `downloadTotal`）是对的，所以这个坑只在兜底时暴露 —— 但如果将来接了 `/traffic`，**不要**把 `up`/`down` 写进累计字段。

### 6.2 WebSocket 可以绕开

`/traffic`、`/logs`、`/memory`、`/connections` 都支持**不带 Upgrade 头**的 GET 流式返回。Android 端直接用：

```java
HttpURLConnection c = (HttpURLConnection) new URL(url).openConnection();
c.setReadTimeout(0);                 // 不要设超时，否则流会被掐断
InputStream in = c.getInputStream(); // 持续读，每行/每个 JSON 对象是"一行数据"
```

因为返回的是**粘连的 JSON 对象**（`{"up":1}{"up":2}...`），需要按花括号配对切分。回环 + 无 TLS，所以不用处理分片、掩码、ping/pong 这些 WS 细节。**省下的是实打实的一两百行协议代码。**

注意：流式连接要跟隧道生命周期绑定（隧道停了就关），否则线程会挂着。

### 6.3 内核接口不能用来「改配置」

配置是**启动时一次生成**的（`MihomoConfig.build()` 写 `config.yaml`）。`PATCH /configs` 只能改运行中的少量字段（`mode`、`log-level` 之类），**改了不会持久化到文件**，下次重连就没了。

所以「改节点池 / 改规则 / 改上游」这类需求，仍然必须走「重新生成配置 → 重启隧道」这条路。接口只负责**读**。

### 6.4 `/proxies` 的 `history` 是「最近几次」，不是统计

`history` 数组长度有限（内核只存最近 10 条左右），用来画曲线可以，用来算「平均延迟」会失真。`delay: 0` 表示超时。

### 6.5 节点名要 URL 编码

`/proxies/香港 01/delay` 里的中文和空格必须编码，否则 404。用 `URLEncoder.encode(name, "UTF-8")`（注意它会把空格编成 `+`，路径里最好再替换成 `%20`）。

### 6.6 无 secret 不等于可以放松

当前 `external-controller` 是 `127.0.0.1:9090` 且没有 `secret`：

- 这是**唯一正确的组合**（回环 + 无认证是安全的；回环 + 有认证是更安全的）；
- **绝对不要**为了「方便调试」把它改成 `0.0.0.0:9090`。这个 API 能把每条连接的域名、进程名、订阅链接全部吐出来；
- 如果哪天加了 `secret`，所有请求都要带 `Authorization: Bearer <secret>`，包括流式那四个。

### 6.7 订阅自带 `external-controller` 时以订阅为准

`MihomoConfig.build()` 只在**缺失**时才追加这一行。如果订阅里写了 `external-controller: 0.0.0.0:9090`，那就是内核实际监听的地址 —— 这种情况下应该**覆盖**它（回环 + 固定端口），否则既连不上 App 期望的端口，也存在暴露风险。

## 7. 一页速查

```bash
# 基础
```
